# Немецкий редактор для base-active-court

Опирайся на немецкий корпус этого репозитория, не меняя смысл продукта ради более гладкого текста.
Пути ниже указаны относительно корня проекта; расположение checkout на диске не фиксировано.
Явное пожелание пользователя для текущей задачи имеет приоритет над выведенными из корпуса предпочтениями.

## Контекст и выбор формулировки

- Перед редактированием прочитай соответствующую часть [словаря и примеров](references/german-style.md).
  Затем найди текущий ключ, соседние строки и место их вывода. Проверяй секцию, устройство и вариант текста:
  одинаковые английские ключи могут означать разные действия.
- Источник терминологии — `app/lang/{common,site,admin,touch,display,widget}/de/`.
  Для модульного текста также проверь `core/modules/{module}/lang/` и фактическую загрузку переводов.
  Следуй `.docs/core/language-system.md`; при расхождении описания с кодом проверь текущую реализацию.
- Для widget учитывай наследование `common → site → widget`, описанное в `.docs/devices/widget.md`.
  Добавляй только нужное отличие, не копируй весь словарь site в widget.
- Существующие тексты неоднородны: они показывают терминологию и контекст, но не подтверждают правильность каждой фразы.
  Не закрепляй опечатки, машинные кальки, английские заглушки и смешение обращений как предпочтения пользователя.

## Обращение и тон

- Для нового общего текста без более точного образца используй вежливое `Sie/Ihr/Ihnen`.
  Это вывод из корпуса, а не запрет на `du`.
- В пошаговой регистрации (`*_step_reg`, `reg_step1`) и последовательно неформальных сообщениях сохраняй `du/dein`.
  В существующем обращении `Du` сохраняй принятую в данном сценарии капитализацию.
  Суффикс `mc_arena` сам по себе не задаёт обращение: тексты этого варианта тоже смешаны.
- Если в редактируемом сообщении смешаны `du` и `Sie`, выбери единое обращение по его сценарию и соседнему экрану.
  Когда контекст не даёт ответа, для нового общего сообщения используй `Sie` и кратко обозначь принятое решение.
  Не переводить весь проект на одно обращение в рамках локальной правки.
- Рабочий вариант для новых строк — стандартный немецкий Германии с `ß`, например `Straße`, `schließen`.
  Это редакторская отправная точка по корпусу, не доказательство региональной настройки конкретной площадки.
  Явно заданная локаль имеет приоритет; не устраивай массовую замену `ss/ß`.
- Стиль: понятный интерфейс спортивного бронирования, короткие действия и конкретные инструкции.
  Для кнопок используй инфинитив (`Buchen`, `Speichern`, `Bestätigen`), для полей — короткие существительные.
  В новом пояснении или ошибке предпочитай факт и доступное следующее действие: `… Bitte wählen Sie …`.
  Сохраняй существующие ограничения длины, подписи, переносы и регистр кнопки, если задача их не меняет.

## Терминология и смысл

- Предпочитай уже используемое название в этом сценарии. Используй словарь в reference для разграничения
  `Buchung/Reservierung`, `Abbrechen/Stornieren/Löschen`, `Guthaben/Gutschrift/Gutschein`, `Zahlbetrag/Abspielbetrag`.
  Не придумывай различия бизнес-статусов только по синонимам в переводах.
- Сохраняй локальные варианты `Kennwort/Passwort`, `Familienname/Nachname`, `Stundenplan/Terminplan/Belegungsplan`.
  Совпадение с подписью реального поля важнее единого синонима во всём проекте.
- Для новых названий спортивного корта используй `Platz/Plätze`, а не буквальную кальку `Spielplatz`.
  Существующие названия административных разделов меняй лишь в пределах поставленной задачи.
- Пиши новые обычные формы `Abo/Abos`, `E-Mail`, `E-Mail-Adresse`, `PayPal`; сохраняй собственные имена и коды продукта.
- Не меняй сроки отмены, суммы, единицы времени, ограничения пароля, правила оплаты, активации или доступности
  исходя из фразы-образца. Сверяй их с поведением затронутого сценария.
  Упоминание `Rechnung` не означает автоматически отдельный от Lastschrift способ оплаты.
- Тексты согласий и оплаты редактируй без изменения объёма согласия, обязательств и утверждений о работе системы.
  Не добавляй обещаний о безопасности, возврате или сроках, которых нет в задаче и реализации.

## Контракт локализации

- Используй существующую локализацию, а не немецкие строки в PHP/JS-шаблонах. Сохраняй ключи и секции при редактуре.
  Новый ключ добавляй в нужную группу или модуль с вариантами `de`, `ru`, `en` по правилам проекта.
  Изменение только немецкой формулировки существующего ключа не требует переписывать другие языки.
- Сохраняй имена и количество вхождений подстановок: `{{sum_price}}`, `{{currency}}`, `{{attribute}}`, `{{0}}`, `%s` и т. п.
  Именованные параметры можно переставить для грамматики. Позиционные параметры сохраняй в исходном порядке.
  Не дописывай `€` или `{{currency}}`, если `{{price}}` уже форматируется вызывающим кодом.
- Сохраняй HTML-структуру, ссылки, классы, идентификаторы, обработчики, сущности и значимые пробелы фрагментов.
  Отдельно различай пустое значение `""` и пробел `" "`: они могут влиять на fallback и видимость блока.
- Здесь собственный парсер `core/system/language/IniFiles.php`, а не обычный `parse_ini_file()`.
  Не перезаписывай файл стандартным INI-сериализатором: в значениях встречаются внутренние кавычки и HTML.
  Держи значение на одной физической строке и сохраняй UTF-8/LF. Не разбивай длинную строку перевода переносами Markdown.
- Существующие внутренние диагностики не являются образцами немецкого интерфейса.
  Применяй разграничение из корневого `AGENTS.md`: системные диагностики на английском,
  пользовательские сообщения — через локализацию, без внутренних подробностей ошибки.

## Проверка результата

Сверь отредактированную строку с соседним экраном: единое обращение, правильные падежи, естественное действие,
сохранённые параметры и исходный смысл. Для составных строк прочитай целое собранное предложение.
Проверь diff на посторонние изменения и согласованность действительно затронутых переопределений.
Если менялся INI, проверь его чтение проектным парсером и сохранность ключей/подстановок подходящим для проекта способом.
Не заявляй проверку Duden или LanguageTool, если она фактически не выполнялась.
