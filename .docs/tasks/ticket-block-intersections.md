## Цель

При каждом добавлении периода абонемента учитывать уже существующие блокировки
площадки и исключать их пересечения из добавляемого диапазона. Единый поток
должен работать при создании нового абонемента, клонировании на новый сезон и
ручном добавлении периода к существующему абонементу.

Использовать гибридную модель:

- при полном перекрытии времени абонемента в конкретный игровой день исключать
  весь день через разрезание `tickets_periods`;
- при частичном перекрытии создавать исключённые игровые слоты в
  `tickets_disabled_time`;
- при наличии `source_type` различать автоматические исключения при добавлении
  периода и обычные отмены клиента или администратора.

## Границы задачи

### Входит в задачу

- Обычные блокировки из `blocks`.
- Периодические и бессрочные блокировки из `blocks_periodical`.
- Проверка блокировок в стандартном `addPeriodToTicket()` для создания,
  клонирования и ручного добавления периода.
- Полное исключение игрового дня через `tickets_periods`.
- Частичное исключение времени через `tickets_disabled_time`.
- Поле-источник исключения и фильтрация истории отмен.
- Производительные индексы для запросов расписания и калькуляции.
- Обновление отчётов и калькуляции с явно заданной семантикой источников.

### Не входит в задачу

- Изменение существующих абонементов при последующем создании блокировки.
- Автоматическое восстановление исключения после удаления блокировки.
- Изменение существующих абонементов при редактировании блокировки.
- Обработка праздников как блокировок в рамках этой задачи.
- Изменение финансовой логики обычной отмены часа абонемента.

После добавления периода сформированные исключения являются частью структуры
абонемента и не зависят от последующего удаления блокировки. Уже сохранённые
даты при перекрывающемся добавлении повторно не пересчитываются.

## Текущее поведение

Абонемент хранится как правило повторения:

- основные параметры — `tickets`;
- диапазоны действия — `tickets_periods`;
- отдельные исключённые слоты — `tickets_disabled_time`.

До реализации при добавлении диапазона проверялись одиночные бронирования и
другие абонементы, но существующие блокировки не изменяли структуру
добавляемого периода.

`tickets_disabled_time` уже используется для отмены отдельного часа
абонемента. Единственный штатный вызов записи выполняется из
`TicketsModelOrder::proceed()` через
`reservation_tickets::addDisabledTimeForTicket()`.

## Требуемая семантика

### Полное перекрытие игрового времени

Пример:

```text
Абонемент: 10:00–12:00
Блокировка: 09:00–13:00
Дата игры: 15.03.2027
```

Дата `15.03.2027` должна быть полностью исключена из диапазонов абонемента.
Исходный период:

```text
01.03.2027–31.03.2027
```

преобразуется в:

```text
01.03.2027–14.03.2027
16.03.2027–31.03.2027
```

Для этой даты строки в `tickets_disabled_time` не создаются.

### Частичное перекрытие времени

Пример для площадки с периодом 30 минут:

```text
Абонемент: 10:00–12:00
Блокировка: 10:30–11:30
Дата игры: 15.03.2027
```

В `tickets_disabled_time` создаются слоты:

```text
15.03.2027 10:30
15.03.2027 11:00
```

Слоты `10:00–10:30` и `11:30–12:00` остаются частью абонемента.

### Периодичность

Перед поиском пересечений необходимо сформировать реальные игровые даты с
учётом:

- `weekdays`;
- `space`;
- `week_begin`;
- `ABO14_TYPE`;
- границ создаваемого периода.

Блокировка в календарную дату, которая не является игровым днём абонемента,
не должна влиять на его структуру.

## Изменение `tickets_disabled_time`

Добавить семантическое поле источника, а не поле отображения. Точная структура
поля в эталонной БД:

```sql
ALTER TABLE `at_base_active_court_tickets_disabled_time`
  ADD COLUMN `source_type` TINYINT UNSIGNED NOT NULL DEFAULT 1
    COMMENT 'Источник исключения: 1 — отмена абонемента; 2 — блокировка при добавлении периода; 3 — ручное исключение'
  AFTER `period_id`;
```

Указанное имя таблицы относится к эталонной БД. Для сайтовых БД необходимо
использовать их фактический префикс через штатный механизм проекта.

Предлагаемые значения:

| Значение | Назначение |
|---|---|
| `1` | `cancellation` — отмена клиентом или администратором |
| `2` | `initial_block` — частичное пересечение с блокировкой при добавлении периода |
| `3` | `manual` — резерв для ручного системного исключения |

Существующие записи после миграции получают `source_type = 1`, поскольку
текущий штатный источник записи — отмена часа абонемента.

Для автоматического исключения значение `price` должно быть `0`, если иное не
будет отдельно установлено финансовыми требованиями.

## Правила использования источника

| Потребитель | Учитываемые источники |
|---|---|
| Расписание | Все |
| Проверка занятости абонементом | Все |
| Калькуляция игровых часов | Все |
| Отчёт фактических часов абонемента | Все |
| История отмен клиента | Только `cancellation` |
| Финансовый возврат | Только `cancellation` |
| Аудит автоматических исключений | `initial_block` |

На схеме с `source_type` автоматическое исключение не должно отображаться как
отмена, выполненная клиентом или администратором. Без поля источник технически
неразличим, но само исключение всё равно сохраняется.

Если бизнес-правила потребуют не учитывать `initial_block` в отчёте
фактических часов, это должно быть отдельным решением: иначе расписание и
отчёт будут показывать разное состояние абонемента.

## План реализации

### 1. Выделить расчёт пересечений

Создать единый сервис или метод, который получает:

- площадку;
- период действия;
- дни недели и периодичность;
- время абонемента;
- период слота площадки;
- обычные, периодические и бессрочные блокировки.

Результат должен разделять пересечения на:

- полностью исключённые игровые даты;
- частично исключённые временные слоты по датам.

Правило пересечения должно работать по интервалам, а не только по совпадению
времени начала слота.

### 2. Изменить стандартный поток добавления периода

Рекомендуемый порядок:

1. Проверить входные данные абонемента.
2. Получить существующие блокировки.
3. Рассчитать игровые даты и пересечения.
4. Сформировать оставшиеся диапазоны `tickets_periods`.
5. Проверить бронирования и другие абонементы только для оставшейся структуры.
6. Для нового абонемента создать `tickets`.
7. Создать рассчитанные `tickets_periods` через `addPeriodToTicket()`.
8. Создать частичные исключения `tickets_disabled_time`; если поле доступно,
   установить `source_type = initial_block`.
9. Проверить целостность созданных записей. Текущие таблицы используют MyISAM,
   поэтому транзакция и rollback для них недоступны: при ошибке ручного
   добавления восстановить прежние периоды и связи исключений, а при создании
   нового абонемента дополнительно удалить строку `tickets`.
10. Обновить iCal/WebIO только после успешного завершения всех операций.

Проверку конфликтов нельзя выполнять только для исходного неразрезанного
диапазона: иначе создание может быть отклонено из-за даты, которая должна быть
полностью исключена.

### 3. Поддержать однодневные диапазоны

Текущий `addPeriodToTicket()` требует `start < finish`. После разрезания может
остаться валидный диапазон из одного дня. Поток создания должен поддерживать
`start <= finish` для такого результата либо использовать отдельный безопасный
метод вставки рассчитанных диапазонов.

Однодневный диапазон создаётся только тогда, когда дата соответствует
игровому дню абонемента.

### 4. Добавить источник в запись исключения

Расширить `addDisabledTimeForTicket()` параметром источника с обратной
совместимостью. Обычная отмена продолжает записываться как `cancellation`, а
автоматическое частичное исключение при добавлении периода — как
`initial_block`.

### 5. Разделить отображение и расчёт

Обновить потребителей `tickets_disabled_time`:

- расписание и проверка занятости используют все источники;
- калькуляция и отчёты фактических часов исключают все источники;
- при наличии `source_type` `TicketsEngine::getArchTicketsByUser()` выбирает
  только `cancellation`;
- при наличии `source_type` персональные данные клиента не показывают
  `initial_block` как отмену;
- при наличии `source_type` финансовая логика возврата не должна запускаться
  для `initial_block`.

`reservation_tickets::getDisabledTime()` сейчас возвращает только времена и
использует статический кэш по диапазону дат. При добавлении фильтра источников
нужно либо:

- хранить `source_type` в кэше и фильтровать результат после загрузки;
- либо включить набор источников в ключ кэша.

### 6. Индексы

В предоставленной эталонной схеме `tickets_disabled_time` имеет только
первичный ключ. После проверки дублей добавить:

```sql
ALTER TABLE `at_base_active_court_tickets_disabled_time`
  ADD UNIQUE KEY `uq_tdt_ticket_date_time`
    (`ticket_id`, `disabled_date`, `disabled_time`),
  ADD KEY `idx_tdt_date_ticket_time`
    (`disabled_date`, `ticket_id`, `disabled_time`),
  ADD KEY `idx_tdt_period_ticket_date`
    (`period_id`, `ticket_id`, `disabled_date`),
  ADD KEY `idx_tdt_ticket_source_date`
    (`ticket_id`, `source_type`, `disabled_date`);
```

Назначение индексов:

- `uq_tdt_ticket_date_time` обеспечивает идемпотентность исключений;
- `idx_tdt_date_ticket_time` ускоряет дневные запросы расписания;
- `idx_tdt_period_ticket_date` обслуживает перенос и удаление исключений при
  разрезании периодов;
- `idx_tdt_ticket_source_date` обслуживает отчёты и историю с фильтром по
  источнику.

В предоставленной схеме `tickets_periods` отсутствует индекс, начинающийся с
`ticket_id`, а `KEY period_id (period_id)` дублирует левую часть первичного
ключа. Добавить индекс для соединений, выборки и удаления периодов абонемента:

```sql
ALTER TABLE `at_base_active_court_tickets_periods`
  ADD KEY `idx_tp_ticket_dates` (`ticket_id`, `start`, `finish`);
```

Удаление существующих избыточных индексов не входит в эту задачу.

### 7. Идемпотентная миграция для 200+ сайтов

Изменение схемы должно быть безопасно для 200+ отдельных сайтовых БД и
повторных запусков.

Основной канал распространения структуры:

1. Добавить поле и индексы в эталонную БД.
2. Проверить результат через `mapi/act.php?view=1`.
3. Распространить структуру через штатный `compareDB`/оркестратор.
4. Зафиксировать результат прогона для каждого сайта.

Не выполнять `ALTER TABLE` внутри каждого запроса расписания, калькуляции или
отчёта. Проверка и изменение структуры должны находиться в централизованном
миграционном шаге либо отдельном репозитории `mapi/act`.

#### Проверка поля

Перед добавлением `source_type` использовать существующий API проекта:

```php
Query::getDB()->checkField('source_type', 'tickets_disabled_time');
```

Собственный запрос к `INFORMATION_SCHEMA` для проверки наличия поля не нужен.

Алгоритм должен быть идемпотентным:

```text
если source_type отсутствует:
    ALTER TABLE ... ADD source_type TINYINT UNSIGNED NOT NULL DEFAULT 1
        COMMENT 'Источник исключения: 1 — отмена абонемента; 2 — блокировка при добавлении периода; 3 — ручное исключение'
иначе:
    проверить тип, UNSIGNED, NULL, DEFAULT и COMMENT
    при необходимости привести к эталонной структуре

UPDATE ... SET source_type = 1
WHERE source_type IS NULL OR source_type NOT IN (1, 2, 3)
```

Нельзя полагаться только на `ADD COLUMN IF NOT EXISTS`: среди сайтов могут
использоваться версии MySQL/MariaDB с разной поддержкой такого синтаксиса.

#### Проверка индексов

Проверять индекс нужно по фактическому составу и порядку колонок, а не только
по имени. На разных сайтах эквивалентный индекс может иметь другое имя.

Для чтения индексов использовать существующий
`Query::getDB()->getIndexes('tickets_disabled_time')`. Основной способ
распространения — штатный `CompareDB`, который сравнивает уникальность, тип и
упорядоченный состав колонок. Собственную проверку через `INFORMATION_SCHEMA`
добавлять не требуется.

Требуемые индексы:

```text
UNIQUE (ticket_id, disabled_date, disabled_time)
INDEX (disabled_date, ticket_id, disabled_time)
INDEX (period_id, ticket_id, disabled_date)
INDEX (ticket_id, source_type, disabled_date)

Для tickets_periods:
INDEX (ticket_id, start, finish)
```

Алгоритм:

```text
получить индексы tickets_disabled_time

если нет уникального индекса с колонками
ticket_id, disabled_date, disabled_time в этом порядке:
    проверить существующие дубли
    после успешной проверки/очистки добавить UNIQUE

если нет индекса с колонками
disabled_date, ticket_id, disabled_time в этом порядке:
    добавить INDEX

если нет индекса с колонками
period_id, ticket_id, disabled_date в этом порядке:
    добавить INDEX

если нет индекса с колонками
ticket_id, source_type, disabled_date в этом порядке:
    добавить INDEX

если в tickets_periods нет индекса с колонками
ticket_id, start, finish в этом порядке:
    добавить INDEX
```

Перед созданием уникального индекса обязательно выполнить preflight:

```sql
SELECT
  ticket_id,
  disabled_date,
  disabled_time,
  COUNT(*) AS rows_count,
  GROUP_CONCAT(disabled_time_id ORDER BY disabled_time_id) AS row_ids
FROM tickets_disabled_time
GROUP BY ticket_id, disabled_date, disabled_time
HAVING COUNT(*) > 1;
```

Если найдены дубли, миграция не должна молча удалять данные. Сайт необходимо
отметить как требующий очистки либо применить заранее согласованное правило
дедупликации с журналированием удалённых идентификаторов.

Все предоставленные таблицы используют MyISAM. `ALTER TABLE` может блокировать
таблицу на время перестроения, поэтому rollout выполнять последовательно и вне
пиковых часов с журналированием длительности каждого изменения.

#### Совместимость во время rollout

Код должен учитывать период, когда часть сайтов уже получила новую версию
приложения, но миграция их БД ещё не завершена:

- если `source_type` отсутствует, существующие строки трактуются как
  `cancellation`;
- SQL не должен обращаться к отсутствующему полю без предварительной проверки;
- добавление периода и исключённого времени разрешается без `source_type`;
  в старой схеме источник не сохраняется, а при наличии поля записывается
  `initial_block`;
- результат проверки структуры кэшируется и не повторяется внутри циклов
  расписания;
- ошибка миграции одного сайта не должна останавливать rollout остальных
  сайтов.

Допустимый rollback к старому коду не требует удаления `source_type` и
индексов: старые `INSERT` содержат явный список полей, а новое поле имеет
безопасное значение по умолчанию.

#### Верификация после миграции

Для каждой сайтовой БД проверить и записать в журнал:

- наличие `source_type`;
- тип `TINYINT UNSIGNED`, `NOT NULL`, `DEFAULT 1` и точный `COMMENT`;
- количество строк, приведённых к `source_type = 1`;
- наличие четырёх требуемых индексов `tickets_disabled_time` либо
  эквивалентных индексов;
- наличие индекса `(ticket_id, start, finish)` в `tickets_periods`;
- наличие необработанных дублей;
- успешность повторного запуска без дополнительных DDL;
- версию/идентификатор миграции и время выполнения.

### Обслуживание периодов

- удаление исключений из полностью вырезанного диапазона.

Отдельно проверить `removePeriodById()`: сейчас метод явно удаляет только
строку `tickets_periods`; необходимо исключить потерянные строки
`tickets_disabled_time` либо подтвердить каскадное ограничение БД.

## Производительность

### Полностью заблокированный день

Предпочтительно разрезание `tickets_periods`:

- день не попадает в выборку расписания;
- не создаётся строка для каждого временного слота;
- меньше данных при длинном игровом интервале.

### Частичное перекрытие

Использовать `tickets_disabled_time`:

- структура уже поддерживает исключение отдельных слотов;
- оставшиеся соседние часы объединяются `buildTimeTickets()`;
- разрезанием дат невозможно выразить частичное время без удаления всего дня.

Расписание всё равно должно читать `tickets_disabled_time` для обычных отмен,
поэтому гибридная модель не добавляет новый тип запроса. Требуется устранить
повторные дневные запросы внутри циклов и загружать исключения за дату одним
индексированным запросом.

## Критерии приёмки

- [ ] Новый абонемент без пересечений создаётся без изменения текущего поведения.
- [ ] Ручное добавление периода учитывает блокировки только на новых датах.
- [ ] Клонирование абонемента на новый сезон проходит через
  `addPeriodToTicket()` и учитывает блокировки нового периода.
- [ ] Перекрывающееся добавление не пересчитывает ранее сохранённые даты и
  исключения абонемента.
- [ ] Остаточные добавляемые диапазоны без единой игровой даты не сохраняются.
- [ ] Период, добавленный раньше исходного `period_start`, сохраняет фазу
  `space` относительно опорных игровых дат и учитывается в отчётах.
- [ ] Полностью перекрытый игровой день отсутствует в `tickets_periods`.
- [ ] Для полностью перекрытого дня не создаются строки `tickets_disabled_time`.
- [ ] Частично перекрытые слоты создаются и без `source_type`; при наличии поля
  они получают `source_type = initial_block`.
- [ ] Незаблокированная часть игрового времени остаётся доступной абонементу.
- [ ] Неигровая дата блокировки не меняет абонемент.
- [ ] Учитываются обычные, периодические и бессрочные блокировки.
- [ ] Корректно работают `space = 1`, `space = 2` и конфигурации `ABO14_TYPE`.
- [ ] Однодневные оставшиеся диапазоны поддерживаются.
- [ ] Пересечения с бронированиями проверяются после исключения блокировок.
- [ ] Пересечения с другими абонементами проверяются после исключения блокировок.
- [ ] На схеме с `source_type` автоматические исключения не отображаются как
  отмены клиента.
- [ ] На схеме с `source_type` автоматические исключения не создают финансовый
  возврат.
- [ ] Расписание, проверка занятости, калькуляция и отчёт фактических часов учитывают автоматические исключения.
- [ ] Удаление или редактирование блокировки после добавления периода не
  восстанавливает исключённые даты и слоты.
- [ ] Ошибка создания не оставляет частично созданные строки `tickets`,
  `tickets_periods` и `tickets_disabled_time`; для текущего MyISAM работает
  компенсирующее удаление.
- [ ] Ошибка ручного добавления восстанавливает прежние периоды и связи
  исключений существующего абонемента.
- [ ] При сохранении или объединении периода существующие исключения внутри
  его диапазона получают актуальный `period_id` по `ticket_id` и
  `disabled_date`, даже если прежняя связь была некорректной.
- [ ] После успешного создания обновляются iCal/WebIO.
- [ ] Миграция создаёт `source_type`, только если поле отсутствует.
- [ ] Поле создаётся как `TINYINT UNSIGNED NOT NULL DEFAULT 1` с согласованным
  комментарием значений `1`, `2` и `3`.
- [ ] Существующие строки получают `source_type = cancellation`.
- [ ] Миграция не создаёт дублирующие эквивалентные индексы.
- [ ] Уникальный индекс создаётся только после проверки существующих дублей.
- [ ] Повторный запуск миграции не генерирует дополнительных изменений.
- [ ] Код сохраняет совместимость с сайтом, на котором миграция ещё не выполнена.
- [ ] Ошибка одной сайтовой БД изолируется и журналируется.
