# План модуля Kurse / Events

> **Статус:** запланировано\
> **Область:** новый модуль Kurse / Events  
> **Последняя проверка:** 2026-09-24\
> **Связанный код:** ещё не создан

Документ фиксирует актуальные требования к модулю `Kurse / Events` для кабинета тренера и клиентского интерфейса.
Курсом управляет основной тренер либо пользователь `users` с отдельным правом `can_manage_courses = 1`.
Право открывает все курсы и назначение/смену основного тренера; общий административный уровень его не заменяет.
Согласование только суммы аренды включается отдельной настройкой.
Подготовлен [проект SQL](courses/src/create.sql); схема не применена к рабочей БД.
Принят вариант B из [ADR-003](../architecture/decisions/adr-003-courses-availability-sources.md): самостоятельная занятость курсов.
Текущий DDL v1.20 содержит 14 новых таблиц, включая общие и персональные условия `trainers_min_max`.
В SQL отражены решения от 18 сентября: возврат всего курса, поздняя запись, бесплатные дополнительные даты,
возврат аренды по длительности, согласование суммы и явная связь оформления со счётом.
Оплату клиентов всегда принимает площадка; аренда и найм различаются распределением средств и расчётами с тренером
([ADR-004](../architecture/decisions/adr-004-courses-venue-payments.md)).
Подробные решения и проверка состава полей: [модель данных](courses/courses-module-analysis-and-plan.md#56-проверка-состава-полей).

Уточнения 24 сентября: персональные тарифы сохраняются; trainers.can_manage_personal_prices отдельно ограничивает их управление конкретным тренером.
Добавлены фото тренера и is_publicly_listed для временного скрытия курса. Архивация означает окончательное завершение.

Реализовать модуль "Kurse / Events" по согласованным требованиям этого плана и закреплённым макетам первого этапа.
Страница https://tsvaltenfurt.ebusy.de/course-module/1327 остаётся историческим референсом и не расширяет согласованный объём.

**1. Архитектура:**
- **Kurs (Курс)** — это группа связанных событий (Events), объединённых по теме, тренеру, возрасту, целям. Kurs не может существовать без хотя бы одного Event.
- **Event (Событие)** — отдельное групповое занятие: дата, время, место, тренер, участники, цена.
- Один Kurs может содержать несколько Events (например, еженедельные занятия в течение сезона).
- Расписание хранится в `course_events`, оформление участия — в `course_enrollments`, выбранные даты — в `course_enrollment_events`.
- `course_events` самостоятельно задаёт занятость площадки; строки в `reservations` и `reservations_tmp_paypal` не создаются.
- `course_event_service_slots` хранит смещение и длительность периодов, выбранные дверные коды и состояния света, отопления и `net`.
  Площадка и абсолютное время наследуются от занятия; источник занятости — занятие целиком, не технические строки.
- Обычные брони, абонементы, блокировки и курсы подключаются к общим проверкам ресурсов и календарям.
  Участники занимают места в группе; состояние оплаты не меняет занятость площадки опубликованным занятием.
- Вид места определяется `area_id`: значение — площадка, `NULL` — внешний адрес конкретного занятия.
  Отдельных `is_other_location` и `location_type` нет; используемая площадка защищена от удаления.
- Вместимость проверяется в БД: `0 < min_participants <= max_participants`; уже занятые места учитывает сервис.

**2. Создание курса и административное управление:**
- Создать отдельную вкладку «Курсы» в админке после семи страниц первого этапа; использовать существующую оболочку и структуру меню.
  Вкладка управляет всеми курсами по `can_manage_courses`; финансовые действия дополнительно требуют штатных прав `accounts`.
- Добавить пункт **"Kurse / Events"** в кабинет клиента с активным профилем тренера.
- В админке пользователей предусмотреть `can_manage_courses`, по умолчанию `0`; выдача требует существующих прав управления `users`.
  В `users.rights` новые уровни не добавляются. Флаг даёт пользователю полное управление всеми курсами, включая создание и выбор тренера.
- Админ выдаёт статус тренера существующему клиенту через создание/активацию `trainers` в рамках прав админки клиентов.
- Реализовать три этапа создания Kurs тренером либо пользователем с правом:
    1. **Общая информация:** название, одно основное фото, описание (WYSIWYG-редактор), место проведения, min/max участников.
       Тренер создаёт курс на себя; пользователь с правом выбирает активный профиль для `trainer_id`.
       Автор — ровно одна ссылка: `created_by_trainer_id` или `created_by_user_id`; сервер берёт фактического инициатора из авторизации.
    2. **График:**
        - Вариант A: **Регулярный Kurs** — указать период (дата начала/окончания), дни недели (Mo, Di…), время (одно на все дни).
        - Вариант B: **Гибкий Kurs** — ручное добавление отдельных Events с разным временем.
        - При создании система генерирует Events и проверяет обычные брони, абонементы, блокировки и занятость тренера.
        - Во втором этапе при публикации создаёт технические периоды с полным покрытием занятия и проверенными параметрами оборудования; в первом публикация не зависит от них.
          Для внешнего адреса без управляемой площадки технические периоды не создаются.
    3. **Договор и готовность цен:**
        - Основной тренер либо пользователь с правом выбирает аренду (`rental`) или найм (`hired`); деньги клиентов принимает площадка.
        - Для внешнего договора фиксированная аренда за весь курс хранится в `trainer_price`.
          `config / courses / rental_approval_required = 1` требует согласования суммы и её изменений с администратором;
          `0` разрешает автономную работу без согласования суммы. Это не согласование публикации или изменения самого курса.
        - В наёмном варианте аренды у тренера нет: `trainer_price = NULL`.
        - Тарифы участия устанавливает и меняет основной тренер либо пользователь с `can_manage_courses = 1`.
        - Цена за **весь Kurs** задаётся по активным типам клиентов из `config_club_state`.
        - В `course_prices` одна строка на `(course_group_id, club_state_id)` с ценами `price_full`, `price_single`
          и отдельной суммой возврата `refund_single_from_full` за одно занятие из полного курса.
          Добавляется цена возврата всего курса `refund_full`; для клиента предусмотрено персональное переопределение.
          Тип клиента определяется по `clients.club_state`; `club_state_id` ссылается на `config_club_state.id`.
        - **"Einzelbuchung erlaubt"** включает покупку отдельных дат через `is_sessions_bookable_separately`;
          цена берётся из `course_prices.price_single`, отдельная таблица цен по датам не создаётся.
        - Полные, разовые и персональные цены задаёт тренер вручную, без автоматического пересчёта.
        - Цены участия независимы от стоимости обычных резервирований и модели взаиморасчётов с тренером.
        - Персональные фиксированные тарифы задаются в `course_participant_overrides` с PK `(course_group_id, client_id)`.
          Отдельного `id` нет; сброс всех переопределений удаляет настройку, сохраняя условия прошлых покупок.
          Персональная разовая цена действует для каждой выбранной даты; отдельного тарифа даты и движка скидок нет.

**3. Тренеры:**
- Роль **"Trainer"** определяется отдельным профилем `trainers` с уникальным `client_id`, активностью и дополнительными сведениями.
- Курс хранит `trainer_id` со ссылкой на профиль; назначение клиента без профиля тренера запрещено.
- Для тренера сервер сопоставляет активный профиль клиента с `course_groups.trainer_id`;
  для пользователя админки проверяет актуальный `users.can_manage_courses`. Дополнительной таблицы ролей курса нет.
- `course_events.trainer_id` задаёт ведущего даты. Замена ведущего не даёт права управлять курсом или отдельным занятием.
- Пользователь с правом полностью управляет всеми курсами: карточкой, публикацией, расписанием, участниками,
  базовыми и персональными тарифами, макетами и рассылками; назначает и меняет основного тренера.
- Профиль тренера такому пользователю не нужен; авторство административной операции сохраняет `users.user_id`.
  У курса/персональных тарифов используется ровно одно из `created_by_trainer_id`/`created_by_user_id`,
  у макетов/правил — ровно одно из `updated_by_trainer_id`/`updated_by_user_id`, с FK и `CHECK`.
- Право проверяется до каждого действия, включая прямые URL и API. После отзыва старое значение в сессии не сохраняет доступ.
  Без флага пользователь не управляет курсом; выдача статуса тренера и согласование аренды остаются отдельными сценариями.
- Смена основного тренера передаёт доступ к курсу и не меняет исторического автора, купленные цены и снимки взаиморасчётов.
  Ведущие уже созданных дат не заменяются автоматически; будущие даты изменяют явно через сервис с проверкой конфликтов.
  Смена стороны действующего договора не переносит прежние обязательства и требует отдельного согласования условий.
- Неактивный профиль не позволяет создавать или менять курсы; история, занятия и покупки сохраняются.
- Подробная связь профиля с клиентом и правила проверки описаны в [модели данных](courses/courses-module-analysis-and-plan.md#52-ключевые-поля).
- Тренер имеет отдельный интерфейс:
    - Просмотр своих Kurse и Events.
    - Создание, публикация и редактирование собственного курса; при действиях тренера автор хранится через его профиль.
    - Просмотр участников (имя, email, статус оплаты).
    - Назначение цен всего курса, отдельных занятий, возврата за одну дату и персональных тарифов при аренде и найме.
    - Фиксированная аренда внешнего договора: согласование суммы и изменений при `rental_approval_required = 1`, автономно при `0`.
    - Отмена занятий своего курса по эффективным условиям `trainers_min_max`, с сохранением истории.
    - Добавление/перенос дат и ручная запись/отмена участия с проверкой сроков, цен, конфликтов и вместимости.
    - Отправка писем участникам.
- Перечисленные операции доступны также пользователю с `can_manage_courses = 1` для любого курса.
  Полное управление сохраняет проверки конфликтов, вместимости, сроков и финансовой истории.

**4. Оплата:**
- Площадка принимает оплату клиентов и выставляет им счета в обоих вариантах; выбора получателя в форме курса нет.
- Управляющий курсом выбирает `trainer_settlement_mode`: `rental` — аренда площадки тренером, `hired` — наёмный тренер.
- `rental`: внешний тренер арендует площадку за фиксированную сумму, учитываемую во взаиморасчётах с ним.
- `hired`: тренер ведёт курс площадки без аренды, получает вознаграждение по условиям найма.
- Правила распределения денег, формулы вознаграждения, удержания и сроки расчётов требуют отдельного определения.
- Цены участия в обоих вариантах определяет основной тренер либо пользователь с отдельным правом курсов.
- `trainer_price` относится только к аренде за весь курс; не является ценой участия или вознаграждением сотрудника.
- `config / courses / rental_approval_required` предусматривает два режима только для суммы внешней аренды:
  `1` — требуется согласование с администратором, `0` — автономный тренер, согласование не требуется.
  По умолчанию для новой установки `0`. При `1` подтверждает любой пользователь с `can_manage_courses = 1`.
  Для наёмного тренера (`hired`) настройка не применяется: аренды нет. Модель взаиморасчётов и согласование — отдельные настройки.
- Сумма не выводится автоматически из обычных тарифов площадки. При `1` новая сумма применяется только после её подтверждения;
  прежняя сумма действует до согласования изменения. Тренер не может отключить требование в форме/API своего курса.
  Пустое/недопустимое значение требует исправления; явное существующее `1` не перезаписывается начальным `0`.
- Согласование публикации, расписания, участников, цен участия и рассылки не требуется.
  До публикации внешнего курса с режимом `1` согласуется только аренда как финансовое условие.
  Хранение конкретной подтверждённой суммы, предложения, версии и пользователя — техническая задача §5.7 подробного плана.
- Режим задаётся до первого оформления; отдельным участникам другой режим не назначается.
- Плательщик — участник (`client_id`). Стоимость курса/занятия фиксируется в оформлении независимо от обычной брони.
- В оформлении сохраняются модель взаиморасчётов и обязательный `settlement_trainer_id` основного тренера для обоих режимов.
- Для полного курса сохраняется условие возврата за одну дату с учётом персонального переопределения:
  `refund_single_from_full = 0.00` — без возврата, положительная сумма — фиксированный возврат.
- Этот тариф задаёт тренер рядом с ценой разового занятия; деление полной цены на число дат не применяется.
- Отдельно задаётся `refund_full` — цена возврата всего курса, ноль означает отсутствие возврата.
  При отказе от оставшегося курса: сохранённая цена возврата × оставшиеся отменяемые занятия / полное число занятий.
  Ранее назначенные возвраты учитываются, итог ограничивается оплаченной суммой; цена покупки не подменяет цену возврата.
- Замена тренера не переписывает тренера в снимках ранее оформленных записей.
- Бесплатное участие задаётся нулевой ценой; отдельного режима `free` нет.
- Способ и состояние оплаты участия хранятся отдельно от модели взаиморасчётов с тренером и оплаты обычной брони.
- Guthaben и Rechnung входят в первый этап: серверный допуск, однократное списание баланса либо подтверждённая запись `unpaid`.
  Сумма по счёту сохраняется для месячного расчёта; формирование через существующий `accounts` и PDF — второй этап.
- BAR vor Ort, PayPal и другие оплаты — второй этап; Lastschrift следует настройкам исполнения счёта,
  доступность конкретного способа определяется настройками площадки и клиента, а не наличием поля в БД.

**5. Изменения и отмены:**
- Основной тренер или пользователь с правом добавляет, переносит и отменяет занятия; история участия сохраняется.
- Административные операции с расписанием и техническими периодами требуют `can_manage_courses` и выполняются через сервис курса;
  независимое изменение отдельных периодов и обход бизнес-проверок запрещены.
- Письма об отмене и переносе относятся к последующему расширению общей очереди и макетов курса;
  сейчас для них не реализуются отправка и обработчики, старые общие шаблоны в SQL не вставляются.
- Перенос согласует занятие, его ревизию, технические периоды и коды, сохраняя ID занятия и участников.
  После commit обновляются календари и оборудование старой и новой площадки.
- Отмена занятия исключает его из действующей занятости и расписания оборудования; технические строки и история участия сохраняются.
  Финансовые обработчики обычных броней не вызываются; наёмному тренеру аренда не начисляется.
- Отмена одного участника не освобождает площадку, пока само занятие остаётся опубликованным.
- Сохранённые дверные коды выдаются по действующему подтверждённому участию, не показываются публично.
  Прекращение выдачи после отмены участия не гарантирует отзыв уже сообщённого кода в устройстве.
- Участник может отменить:
    - Весь Kurs; возврат от отдельной цены `refund_full` пропорционально неиспользованным занятиям, с сохранением расчёта.
    - Отдельное Event в срок, включая дату из полного курса; флаг отдельной покупки не запрещает такую отмену.
- Участник использует `cancel_days_limit`, сохранённый в оформлении при покупке.
- Для организатора планируется `trainers_min_max`: условия по умолчанию и персональные условия основного тренера курса.
  Персональное значение имеет приоритет; `NULL` наследует общее, `0` означает явное нулевое значение.
  Формула календарной границы та же, что у обычных броней; таблица `areas_min_max` и её значения не меняются.
  Срок по умолчанию — 1 календарный день. Администратор с правом курсов редактирует условия, тренер их просматривает.
- При своевременной отмене аренды администратор выбирает `none` — без уменьшения суммы, либо `proportional` — пропорциональное уменьшение.
  Пропорция считается по длительности: аренда курса × длительность отменяемых занятий / общая длительность занятий по договору.
  Длительности и результат сохраняются; повтор не уменьшает аренду второй раз. Фактическая выплата автоматически не выполняется.
  После срока отмена отклоняется; у наёмного тренера аренды нет, административного обхода срока нет.
- Ручная отмена участия тренером также проверяет срок участника; отмена самого занятия использует срок организатора.
- Сумма возврата участнику за одну дату берётся из снимка покупки; при нуле новый `refund_required` не создаётся.
  Положительную сумму передают площадке для обработки возврата. Выплата автоматически не выполняется;
  влияние возврата на взаиморасчёты с тренером определяется отдельно по сохранённым модели и тренеру.
- В существующих таблицах курса, занятия, оформления и участия сохраняются `cancellation_parameters`:
  инициатор, применённые условия и результат. Отдельной таблицы истории или журнала выплат нет.
- Для полного отказа сохраняются цена возврата, полное число дат, оставшиеся даты и итог;
  для аренды — выбранный способ, договорная сумма и доля. Повтор не назначает возврат второй раз.
- Полный порядок и состав снимков: [отмена занятия или курса](courses/courses-module-analysis-and-plan.md#88-отмена-занятия-или-курса).

**6. Уведомления:**
- Подготавливаются только SQL и контракт данных; внешний процесс, cron, интерфейс и отправка пока не реализуются.
- Общая `scheduled_events` хранит тип действия, время запуска, параметры, состояние и результат.
  Для всех писем курса используется обработчик `course_email_send`; произвольный макет не требует новой функции.
- У курса может быть несколько произвольных макетов. Основной тренер создаёт их, задаёт название, тему и тело.
  `course_email_templates` хранит карточку, `course_email_template_translations` — тему и тело каждого языка.
  Название, `lesson_reminder_enabled`, общая ревизия и автор находятся только в карточке.
- Каждый макет допускает отправку немедленно, на заданную дату/время и периодически.
  `lesson_reminder_enabled = 1` отдельно включает напоминания перед занятиями; `0` отключает только их.
  Общего переключателя, ограничивающего макет одним способом отправки, нет.
- Интервал `course_groups.reminder_minutes_before` общий для включённых макетов; `0` отключает напоминания.
  Для каждого подтверждённого участника каждой даты и каждого включённого макета создаётся отдельное задание.
  Ключ содержит ID оформления, занятия, макет и ревизию занятия. Переводы не создают дополнительных писем.
- Для `automatic` перед отправкой повторно проверяются участие, состояние даты, будущий старт,
  актуальная ревизия, интервал курса и включение выбранного макета.
  Перенос, смена интервала и выключение макета согласуют автоматические задания; прекращение участия/курса касается писем по участию.
- Для разовой рассылки тренер выбирает макет и «сейчас» либо дату/время. Получатели: отдельные участники, весь курс,
  любые клиенты из общей базы либо один/несколько введённых email. Источники можно объединить в одной постановке.
  Привязка к занятию необязательна: можно отправить общее сообщение выбранным участникам курса.
  В списке курса один клиент учитывается один раз независимо от количества его оформлений.
- `trigger_type = manual` сохраняется и при разовом планировании на будущее; периодические запуски используют `recurring`.
  `scheduled_at = available_at` получают выбранное время в UTC; время отправки хранится у задания, не у макета.
  Местное время и часовой пояс показываются перед подтверждением; явно прошедшее или некорректное время отклоняется.
- Ручное задание связано с курсом (`source_type = course`) либо датой (`course_event`).
  При постановке фиксируются `request_id`, отпечаток запроса, режим/тип адресата, email, макет и готовое письмо.
  Инициатор — `initiator_type = trainer|admin` и `initiator_id` профиля тренера либо пользователя с правом курсов.
  В `payload` формат версии 2: `recipient_type = client` и положительный `client_id` либо `email` и `client_id = null`.
  `recipient_mode = direct` обозначает прямое разовое письмо, не зависящее от участия или состояния курса.
  Для разового «весь курс» берётся действующий состав на момент подтверждения; для периодического — заново на каждом запуске.
  Новый участник не добавляется в уже согласованную пачку автоматически.
- Адреса проверяются до постановки; дубли исключаются, конфликт профилей/языков/режимов на один email уточняется в предпросмотре.
  Ключ разового задания использует UUID запроса и хеш адреса; email без карточки не требует фиктивного `client_id`.
- Повтор запроса сверяет сохранённый отпечаток и возвращает прежние задания без повторного чтения контактов/состава курса.
  Новая намеренная рассылка получает новый `request_id`.
- Внешний процесс исполняет задание не раньше `available_at`, даже если интерфейс передал его ID сразу после commit.
  До результата обработки интерфейс показывает планирование или очередь, затем индивидуальные результаты.
- Изменение или удаление макета, выключение автоматики и перенос даты не меняют снимки ручной рассылки.
  Отписка, окончание/отмена курса и отмена контекстной даты прекращают письма по участию, включая ручные.
  Прямые `manual + direct` сохраняются: адрес и содержание уже подтверждены независимо от курса.
  Ожидающее письмо можно явно отменить, включая повтор после ошибки; время меняется только до первой попытки.
  Новое содержание/получатели требуют новой постановки.
- Редактор предусматривает все активные языки `LangConfig`; включение напоминаний/периодического правила и постановка требуют готовых переводов.
  Сохранение карточки и переводов выполняется одной транзакцией с обновлением общей ревизии и автора.
- Параметры в теме и теле используют формат `%KEY%`: `%CLIENT_NAME%`, `%CLIENT_SURNAME%`, `%EMAIL%`,
  `%COURSE_TITLE%`, `%DATE%`, `%PERIOD%`, `%PLACE_TITLE%`, `%EVENT_START%`, `%EVENT_FINISH%`, `%TRAINER_NAME%`.
  Для параметров даты/периода/места нужно выбрать занятие; без него доступны данные адресата, курса и основного тренера.
  Для введённого email язык выбирает тренер; имя/фамилия вводятся по желанию либо заменяются пустыми строками.
  Для выбранного клиента контакты и язык берутся из карточки при постановке; изменение карточки не меняет готовое письмо.
  Неизвестные параметры и отсутствие нужного контекста отклоняются, предпросмотр использует ту же подстановку.
- Напоминание фиксируется перед первой попыткой, разовое письмо — при постановке, периодическое — при создании очередного запуска.
  Повторы одной попытки используют снимок; следующий календарный запуск берёт актуальные тексты. Общая `letters_templates` не изменяется.
- Отправитель — системный email домена, адрес тренера — `Reply-To`; одно письмо одному получателю.
  Процесс защищает обработку токеном; неизвестный результат SMTP требует проверки без автоматического повтора.
- Периодические правила хранятся в `course_email_schedules`, выбранные получатели — в `course_email_schedule_recipients`.
  Один макет может иметь несколько правил. `recipient_mode = selected` — выбранные действующие участники;
  `course` — весь актуальный состав курса/контекстной даты, без дублирования списка в таблице получателей.
- Правило содержит интервал в календарных днях, местное время, IANA-зону, первую/последнюю даты, состояние и курсор UTC.
  Пример: `interval_days = 1`, `send_time = 12:00:00`, `timezone = Europe/Berlin` — ежедневно в местные 12:00;
  `7` — раз в неделю от первой даты. Новое правило сохраняется в паузе; включение требует готового макета,
  действующего курса и корректного режима выбора; `course` допускает пока пустой состав.
- Внешний процесс находит наступившие `active`-правила по `next_run_at` и одной транзакцией создаёт письма и продвигает курсор.
  Задания имеют `trigger_type = recurring`, `source_type = course_email_schedule` и ID правила.
  Ключ включает правило, календарный момент и клиента. Каждый запуск получает новые задания, старые результаты сохраняются.
- На каждом запуске заново отбираются действующие участники согласно режиму; имена, адреса и тексты фиксируются в очереди.
  Выбранный ID не разрешает письма после отписки. Пустой текущий состав пропускает запуск с продвижением курсора.
- Пауза, возобновление и правка расписания повышают его ревизию и отменяют все ожидающие периодические письма,
  включая повторы после ошибки. Разовые письма и напоминания перед занятиями этим действием не затрагиваются.
  Штатное завершение по `end_date` не меняет ревизию; последняя пачка допустима только пока курс и участие действуют.
  Отмена контекстного занятия приостанавливает его правила. Окончание/отмена/архивация курса завершает все его правила.
- Для напоминаний, периодических и разовых писем по участию перед каждой попыткой проверяются курс и основания участия.
  Прямые разовые письма проверяют сохранённое задание, срок и токен, без зависимости от участия/состояния курса.
  Нужны подтверждённые связи с ещё не окончившимися `scheduled`-занятиями; история прошедших дат участия не продлевает.
  Отмена одной даты не прекращает общие письма, если у клиента остаются другие действующие даты.
- Отписка отменяет ожидающие письма по участию клиенту; окончание курса — всем участникам, включая разовые и повторы.
  Явно адресованные `manual + direct` исключаются из массовой отмены и остаются в очереди до отправки или явной отмены.
  Курс окончен для рассылки, когда нет `scheduled`-занятия с `finish_at` позже текущего времени.
  Черновики и отменённые/проведённые даты не продлевают срок; `end_date = NULL` не отменяет это правило.
  История сохраняется, старые задания после новой записи не возобновляются.
- Следующий момент считается по местному календарю, поэтому переход часов не сдвигает «ежедневно в 12:00».
  Несуществующее время пропускается, повторяющееся осенью используется один раз. Простой не создаёт пачку всех пропущенных дней.
- Отдельных журнала рассылок, второй очереди и копий макетов для ручного способа нет.
  Автоматические реакции на подтверждение/отмену/перенос остаются последующим расширением;
  приглашение незаписанному или письмо после окончания курса уже можно предусмотреть как прямую разовую отправку.
  Произвольные email не добавляются в периодические правила; новых таблиц или записей клиентов для них не создаётся.
- [Подробный порядок](courses/courses-module-analysis-and-plan.md#89-уведомления). В SQL 14 новых таблиц,
  право в существующей `users` и одна настройка `config`; схема не применена к рабочей БД.

**7. Отображение для пользователей:**

Новые страницы перечислены отдельно в [§8.12 подробного плана](courses/courses-module-analysis-and-plan.md#812-перечень-новых-страниц).
Перечень включает шесть страниц курсов/тренеров и ранее согласованную страницу «Мои курсы»;
корректировки существующих страниц в него не входят.

- **Страница "Kurse / Events"** в меню:
    - Список активных Kurse с опубликованными занятиями.
    - Фильтр по дате; категории и возрастные фильтры требуют отдельного согласования и пока не поддержаны схемой.
    - Каждый Kurs: название, период, место, тренер, статус (frei/voll), кнопка "Buchen".
    - При клике — детали Kurs и бронирование.
- **Курсы на недельном отображении:** отдельная страница с занятиями по дням выбранной недели и переходом к карточке курса.
- **Страницы тренеров:** публичный список и детальная страница тренера; управление собственными курсами — в личном кабинете тренера.
- **Календарь площадок:**
    - Общий слой собирает обычные брони и самостоятельные занятия курса; курс получает цвет и переход к карточке.
    - Технические периоды не создают дополнительных событий календаря.
    - При клике — переход на страницу Kurs.
    - Нельзя бронировать из календаря.
- **«Мои курсы» в панели авторизованного клиента:**
    - Пункт показывается рядом с данными пользователя и открывает отдельную страницу персонального отчёта.
    - Отчёт содержит только собственные записи: текущие и историю, купленные даты, тренера, место, стоимость и состояния оплаты/участия.
    - Предусмотрены пустое состояние и самостоятельная отмена по ранее согласованным правилам; новые таблицы не нужны.
    - [Подробный контракт](courses/courses-module-analysis-and-plan.md#811-мои-курсы-пункт-панели-и-персональный-отчёт).

**8. Бронирование:**
- Можно записаться:
    - На весь Kurs (по цене Kurs).
    - На отдельное Event (если разрешено).
- Запись создаёт `course_enrollments`, купленные даты — `course_enrollment_events`; персонального списка допуска к датам нет.
- `course_participant_overrides` меняет только тарифы и не создаёт запись или занятое место.
- Если Kurs уже начался — покупка может включать только будущие Events;
  полная покупка оставшейся части стоит сумму её занятий по разовым тарифам с персональными переопределениями.
  Сохраняется право полной покупки; каждая новая опубликованная дата автоматически добавляется бесплатно всем действующим полным записям.
  Частичные покупки не расширяются, полностью отменённые не возобновляются; вместимость проверяется атомарно до публикации.
- При заполнении max участников — "Dieser Kurs ist leider bereits voll belegt".

**9. Оплата и счета:**
- Первый этап: Guthaben и ежемесячный расчёт по счёту по доступности клиенту/площадке. Оплату принимает площадка.
- Guthaben списывается идемпотентно; баланс, места и цена проверяются совместно. По счёту сохраняется confirmed/unpaid.
- Формирование документов и PDF — второй этап, в рамках существующего месячного процесса.
- DDL v1.20 допускает один месячный invoice_account_id для нескольких оформлений; отсутствие документа в этапе 1 штатно.
- Остальные оплаты, финансовые отчёты и фактические выплаты — второй этап. Аренда/найм и права сохраняются.
- [Подробный контракт оплаты](courses/courses-module-analysis-and-plan.md#85-сбор-оплаты-guthaben-и-ежемесячный-счёт).

**10. Конфликты:**
- Блокировка площадки блокирует Kurse.
- При создании Kurs система проверяет:
    - Доступность площадки.
    - Занятость тренера.
    - Обычные резервирования площадки.
    - Пересечения с другими занятиями курсов.
- При конфликте — предупреждение + запрет на создание.
- Для площадки используется общий слой пересечений обычных броней, абонементов, блокировок и курсов.
- Все пути записи ресурсов проверяют курсы под общей блокировкой; подключаются сайт, админка, терминалы, API и фоновые операции.
- Для первого этапа все проверки занятости учитывают курсы. Выдача кодов, WebIO и технические экспорты/управление оборудованием подключаются во втором этапе.
- Для тренера дополнительно проверяются пересечения занятий между разными площадками и внешними адресами.
