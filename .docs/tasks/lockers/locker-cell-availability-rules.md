# Возможные правила доступности ячеек

**Дата создания:** 2026-07-07  
**Статус:** возможность для будущей реализации  
**Связанный документ:** [locker-system-plan.md](locker-system-plan.md)

---

## 1. Назначение

Документ описывает возможное расширение логики доступности ячеек шкафчиков.

В MVP эти правила **не реализуются**. Базовая доступность определяется только:

```text
locker_cells.active = 1
locker_area_cells.active = 1
нет пересечения с active locker_reservations
```

Расширение можно добавить позже внутри `LockerAvailabilityService`, не меняя клиентский сценарий выбора ячеек.

---

## 2. Точка расширения

Рекомендуемая точка для будущей логики:

```php
public function isCellAvailableForContext(
    int $cellId,
    int $areaId,
    DateTimeInterface $start,
    DateTimeInterface $finish
): bool;
```

В MVP метод проверяет:

1. Ячейка активна.
2. Ячейка привязана к выбранной площадке.
3. Нет активной записи `locker_reservations` с пересечением времени.

Позже в этот же метод можно добавить:

- ограничения по длительности;
- расписание по времени суток;
- расписание по дням недели;
- исключения по датам.

---

## 3. Вариант A: ограничение по длительности

Нужно, если разные ячейки можно бронировать только на определённую длительность.

Примеры:

```text
Маленькая ячейка — максимум 60 минут
Большая ячейка — от 90 минут
VIP ячейка — только на 2+ часа
```

Возможные поля в `locker_cells`:

```text
min_duration INT NULL
max_duration INT NULL
```

Единица измерения — минуты.

Проверка:

```text
duration = finish - start

если min_duration не NULL и duration < min_duration → недоступна
если max_duration не NULL и duration > max_duration → недоступна
```

Оценка сложности: низкая, примерно 0.5-1 день с админкой и проверками.

---

## 4. Вариант B: простое расписание по времени суток

Нужно, если ячейка доступна только в определённые часы.

Примеры:

```text
A-01 доступна с 08:00 до 22:00
VIP ячейка доступна только с 18:00 до 23:00
```

Возможные поля в `locker_cells`:

```text
available_from TIME NULL
available_to TIME NULL
```

Проверка:

```text
если available_from не NULL и start_time < available_from → недоступна
если available_to не NULL и finish_time > available_to → недоступна
```

Особое внимание нужно уделить ночным интервалам, например `22:00-02:00`.

Оценка сложности: средняя, примерно 1-2 дня.

---

## 5. Вариант C: расписание по дням недели

Нужно, если доступность ячейки зависит от дня недели.

Примеры:

```text
A-01 доступна только по будням
B-01 доступна в субботу и воскресенье
VIP ячейка доступна только вечером по пятницам
```

Возможная таблица:

```text
locker_cell_timetable
- id
- cell_id
- weekday
- time_from
- time_to
- active
```

`weekday` можно хранить как число `1-7` или в формате, принятом в проекте.

Проверка:

```text
найти active правило для cell_id + weekday
проверить, что start/finish попадает в time_from/time_to
```

Оценка сложности: средняя/высокая, примерно 3-5 дней с админкой.

---

## 6. Вариант D: исключения по датам

Нужно, если есть разовые исключения:

```text
ячейка недоступна 2026-08-01 из-за ремонта
VIP ячейка доступна в праздничный день по другому графику
```

Возможная таблица:

```text
locker_cell_timetable_exceptions
- id
- cell_id
- date
- time_from
- time_to
- is_available
- comment
```

Такие исключения должны иметь приоритет над обычным расписанием.

Оценка сложности: высокая, особенно если нужна удобная админка.

---

## 7. Рекомендация

Для MVP не добавлять поля и таблицы расписаний.

Оставить только архитектурную точку расширения:

```text
LockerAvailabilityService
```

И текущие проверки:

```text
active + area binding + no reservation overlap
```

Когда появится конкретное бизнес-правило, добавить минимальный вариант:

1. Сначала `min_duration` / `max_duration`, если нужна длительность.
2. Затем `available_from` / `available_to`, если нужны часы.
3. Отдельные timetable-таблицы добавлять только при реальной необходимости.
