# Правила ведения документации

## Назначение

Документация проекта хранится в `.docs/`. Корневой `.docs/README.md` является основной точкой навигации.
Документы должны описывать фактическое устройство системы, принятые архитектурные решения и подготовленные
планы без дублирования одного содержания в нескольких разделах.

## Обязательное чтение

Перед изменением функциональности необходимо:

1. Открыть `.docs/README.md`.
2. Прочитать документацию соответствующего модуля в `.docs/modules/{module}/`.
3. При необходимости прочитать связанные разделы `architecture`, `core`, `engines`, `devices`, `technical` или `development`.
4. Перед добавлением или запуском тестов прочитать `.docs/development/testing.md` и `../tests/README.md`.

## Размещение документов

| Раздел | Содержание |
|---|---|
| `architecture/` | Общая архитектура, границы подсистем и основные принципы. |
| `core/` | Системные компоненты ядра. |
| `engines/` | Движки и правила работы с данными. |
| `devices/` | Поведение site, admin, touchscreen, display и mapi. |
| `technical/` | Технические контракты и сквозные механизмы. |
| `development/` | Правила разработки, тестирования, миграций и сопровождения. |
| `installation/` | Установка, серверные требования и эксплуатационная настройка. |
| `modules/{module}/` | Текущее поведение модуля, планы его развития и подробные описания функций. |
| `sites/` | Спецификации, кастомизации и требования отдельных установок Active Court. |
| `tasks/` | Краткий реестр активных задач и отдельные планы без подходящего модульного раздела. |
| `improvements/` | Реестр предполагаемых улучшений и их короткие карточки. |
| `archive/` | Отчёты о выполненной работе, завершённые задачи и исторические реестры. |

Подробный план модульной функции размещается в `.docs/modules/{module}/`. В `.docs/tasks/README.md` для него
добавляется только короткое описание и ссылка. План не следует хранить в `reports/`, если он не является
запрошенным отчётом.

## README-файлы

README можно создавать, когда он нужен как:

- обзор раздела или модуля;
- навигационный индекс нескольких связанных документов;
- краткий реестр со ссылками на подробные материалы.

README не создаётся только ради наличия файла и не дублирует подробное содержание тематических документов.
При добавлении нового README необходимо включить в него существующие основные документы раздела и обновить
ссылку в родительском навигационном файле, если такой файл существует.

## Задачи и улучшения

`.docs/tasks/README.md` содержит компактный перечень задач. Для каждой задачи достаточно названия, краткого
описания и пути к подробному плану. Архитектурные детали, этапы и критерии приёмки остаются в документе плана.

`todo.md` и `ideas.md` перенесены в архив как исторические источники. Новые задачи
регистрируются в `README.md` и получают отдельный файл плана либо ссылку на документацию модуля. Завершённый
план удаляется из активного реестра и переносится в `.docs/archive/tasks/` с записью в архивном README.

`.docs/improvements/README.md` является реестром предполагаемых улучшений. Подробности не должны дублироваться
между реестрами задач, улучшений и модульной документацией.

## Отчёты

Файлы в `.docs/archive/reports/` создаются, когда пользователь явно запросил итоговый отчёт либо отчёт уже
является частью задачи. Отчёт фиксирует выполненную работу или результаты анализа, содержит дату и ссылки на
затронутую документацию. План будущей реализации сам по себе отчётом не является. Каждый отчёт добавляется в
`.docs/archive/reports/README.md`.

## Именование

- Для новых файлов использовать нижний регистр и дефисы: `payment-processing.md`.
- Не использовать пробелы, подчёркивания и `camelCase` в именах документации.
- Стандартный навигационный файл называется `README.md`.
- Правило применяется к документации в `.docs/` и её подпапках.
- Существующие пути, связанные с историческим именем модуля, например `modules/webIo`, не переименовываются без
  отдельной задачи по миграции ссылок.

## Обновление документации

При функциональном или архитектурном изменении необходимо:

1. Обновить документ, который уже отвечает за изменённое поведение.
2. Добавить новый документ только при отдельном назначении или значительном самостоятельном объёме темы.
3. Обновить README, оглавления и перекрёстные ссылки.
4. Не оставлять одновременно старое и новое описание одного поведения.
5. Не переносить внутренние exception, secrets, credentials или PII в документацию и примеры.

## Язык и версия PHP

Проектная документация и поясняющие комментарии могут быть на русском языке. Пользовательские сообщения в коде
не хардкодятся и проходят через локализацию; внутренние диагностические сообщения пишутся на английском.

Серверный runtime проекта - PHP 8.2. Примеры кода, команды установки и требования совместимости должны быть
рассчитаны на PHP 8.2. Документация должна указывать эту версию как серверную и не предлагать другие версии
как минимально допустимые.


## Карточка активного плана

Активный план или задача начинается с краткой карточки сразу после заголовка:

```markdown
> **Статус:** запланировано | в работе | частично реализовано | требует актуализации
> **Область:** модуль или подсистема
> **Последняя проверка:** YYYY-MM-DD
> **Связанный код:** `путь/к/коду/`
```

Статус должен описывать фактическое состояние, а не ожидаемый результат. Дата последней проверки обновляется только после сверки документа с текущим проектом. Если код ещё не создан или находится в другом репозитории, это указывается явно.

## Автоматическая проверка

После изменения структуры, перемещения документов или обновления требований PHP запустите:

    composer docs:check

Без Composer используется эквивалентная команда:

    php bin/check-documentation

Кроссплатформенная PHP-команда проверяет локальные ссылки, обязательные индексные файлы, отсутствие документов в устаревших каталогах и требования к серверной версии PHP 8.2. Архивные документы исключены только из проверки актуальности версии PHP; их локальные ссылки по-прежнему должны работать.

## Архитектурные решения

Решения, которые задают долгосрочные архитектурные ограничения или меняют взаимодействие подсистем, фиксируются в `architecture/decisions/`. Используйте [шаблон ADR](../architecture/decisions/adr-template.md), добавляйте новый документ в [реестр](../architecture/decisions/README.md) и не изменяйте историю принятого решения задним числом.

Эксплуатационные инструкции и ссылки на связанные планы собираются в [разделе operations](../operations/README.md). Индекс не должен копировать подробные инструкции из разделов установки и разработки.
