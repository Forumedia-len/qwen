# Логирование действий администратора

**Дата создания:** 2026-07-07  
**Статус:** возможный вариант реализации  
**Область:** общая архитектура админки, не привязано к конкретному модулю

---

## 1. Назначение

Документ фиксирует возможный подход к хранению действий, выполненных администраторами в админке.

Цель — отделить техническое логирование и бизнес-таблицы от audit log:

- бизнес-таблицы хранят актуальное состояние сущностей;
- `created_at` / `updated_at` в бизнес-таблицах показывают время создания и последнего изменения записи;
- audit log показывает, кто именно изменил данные, что изменилось и откуда было выполнено действие.

---

## 2. Возможная таблица

```text
admin_action_log
- id
- admin_id
- module
- entity_type
- entity_id
- action
- old_values
- new_values
- ip
- user_agent
- request_id
- created_at
```

| Поле | Тип | Назначение |
|------|-----|------------|
| `id` | INT PK | Идентификатор записи журнала |
| `admin_id` | INT FK | Администратор, выполнивший действие |
| `module` | VARCHAR | Модуль: `areas`, `clients`, `lockers`, `webIo` |
| `entity_type` | VARCHAR | Тип сущности: таблица или доменное имя модели |
| `entity_id` | INT NULL | ID изменённой сущности, если применимо |
| `action` | VARCHAR | Действие: `create`, `update`, `delete`, `activate`, `deactivate`, `manual_open` |
| `old_values` | JSON/TEXT NULL | Значения до изменения |
| `new_values` | JSON/TEXT NULL | Значения после изменения |
| `ip` | VARCHAR NULL | IP администратора |
| `user_agent` | TEXT NULL | User-Agent запроса |
| `request_id` | VARCHAR NULL | ID запроса для связи с техническими логами |
| `created_at` | DATETIME | Когда действие было зафиксировано |

## 3. Пример записи

```json
{
  "admin_id": 5,
  "module": "lockers",
  "entity_type": "locker_cells",
  "entity_id": 12,
  "action": "update",
  "old_values": {
    "price": "5.00",
    "active": 1
  },
  "new_values": {
    "price": "7.00",
    "active": 0
  },
  "ip": "192.168.1.10",
  "created_at": "2026-07-07 14:35:20"
}
```

---

## 4. Какие действия логировать

Минимальный набор:

- создание записи;
- изменение записи;
- удаление записи;
- включение / отключение записи;
- ручные административные действия, которые меняют состояние системы;
- операции, влияющие на деньги, доступ, оборудование или клиентские данные.

Не обязательно логировать:

- открытие страниц списка;
- фильтрацию и поиск;
- обычные GET-запросы без изменения состояния;
- повторяющиеся технические фоновые операции, если они уже покрыты системными логами.

---

## 5. Правила хранения значений

`old_values` и `new_values` должны хранить только изменённые поля, а не полный снимок всей записи.

Пример:

```json
{
  "old_values": {
    "active": 1
  },
  "new_values": {
    "active": 0
  }
}
```

Чувствительные данные не должны попадать в audit log:

- пароли;
- токены;
- платёжные данные;
- cookie/session идентификаторы;
- персональные данные без необходимости для аудита.

---

## 6. Связь с другими логами

Audit log не заменяет техническое логирование.

| Тип | Что хранит |
|-----|------------|
| Технический лог | Ошибки, исключения, отладочные сообщения, системные события |
| HistoryService | История выполнения конкретной операции или сценария |
| `admin_action_log` | Кто в админке изменил данные и какие поля поменялись |

Если в системе есть `request_id`, его стоит писать и в технические логи, и в `admin_action_log`, чтобы связывать действия администратора с ошибками или побочными эффектами.

## 7. Варианты реализации

### 7.1. Общий сервис

```php
AdminActionLogger::log(
    adminId: $adminId,
    module: 'lockers',
    entityType: 'locker_cells',
    entityId: $cellId,
    action: 'update',
    oldValues: $oldValues,
    newValues: $newValues
);
```

Подходит, если нужно единое поведение во всех модулях.

### 7.2. Trait для admin-моделей

Модель или контроллер получает общий метод:

```php
$this->logAdminAction('update', $entityId, $oldValues, $newValues);
```

Подходит, если в проекте уже есть общий базовый класс для admin CRUD.

### 7.3. Логирование на уровне контроллера

Контроллер явно пишет лог после успешного изменения.

Плюс: проще внедрять точечно.  
Минус: выше риск забыть лог в одном из действий.

---

## 8. Рекомендация для MVP

Для MVP достаточно:

- одной общей таблицы `admin_action_log`;
- логирования `create`, `update`, `delete`, `activate`, `deactivate`;
- хранения только изменённых полей;
- записи `admin_id`, `module`, `entity_type`, `entity_id`, `action`, `old_values`, `new_values`, `created_at`;
- добавления `ip` и `user_agent`, если они доступны без усложнения кода.

Расширения вроде просмотра diff в UI, фильтрации по request_id и экспорта можно добавить позже.
