# Онлайн-оплата: PayPal / Payone (модуль оплаты и конфиг)

Документ фиксирует **текущее** поведение онлайн‑оплаты: где настраивается, как выбирается провайдер, как хранятся профили и как они применяются в рантайме.

## Админка: где настраивается

Раздел настроек «Online‑Zahlung» работает через `mode=online_payment`:

- **Gateway**: `config.php?mode=online_payment&tab=gateway`
  - CRUD профилей учётных данных **для выбранного primary** (PayPal или Payone).
- **Guthaben**: `config.php?mode=online_payment&tab=guthaben`
  - предложения пополнения счёта (Guthaben);
  - блок выбора основного провайдера и включения онлайн‑оплаты.

## Онлайн-счета бронирований

Функция создаёт отдельный счёт после успешной онлайн-оплаты бронирования через прямой PayPal NVP или Payone. Пополнение личного счёта (`Guthaben`) продолжает использовать предоплатные счета и не относится к этому типу.

### Настройка и подготовка БД

Функция включается отдельно от самой онлайн-оплаты:

- страница: `accounts.php?action=showAccountTextConfig`;
- поле формы: чекбокс с `label` «Создавать счета для онлайн-оплат»;
- строка настройки сохраняет стандартные две ячейки таблицы, а чекбокс и его `label` находятся во второй ячейке;
- конфигурация: `config.type = account`, `config.alias = online_payment_invoice_use`;
- значение по умолчанию: выключено;
- чекбокс показывается только при включённом `payment.online_payment_use`;
- единая runtime-проверка: `AccountConfig::useOnlinePaymentInvoice()` / `config('account')->useOnlinePaymentInvoice()`;
- создание разрешено только при одновременном включении `payment.online_payment_use` и `account.online_payment_invoice_use`.

При активации `OnlinePaymentInvoiceInstallEngine::ensureInstalled()` проверяет `accounts.account_type`:

- целочисленные типы принимаются без изменения;
- `CHAR`/`VARCHAR` принимаются, если вмещают значение `5`;
- для `ENUM` идемпотентно добавляется значение `'5'` с сохранением `NULL`, `DEFAULT`, `COLLATE` и комментария столбца;
- `ALTER TABLE` выполняется через отдельное подключение `Query::sqlQueryWithExtendedPrivileges()` и не переключает основное подключение сайта;
- отсутствующая таблица/колонка или неподдерживаемый тип блокируют включение настройки;
- настройка сохраняется как включённая только после успешной проверки/миграции структуры;
- ошибка показывается администратору и записывается в журнал `accounts`.

Новая таблица бронирований для счёта не создаётся: используется существующая `accounts_reservations`.

### Типы, коды и нумерация

В БД новый тип закреплён как `AccountType::OnlinePayment`:

- `accounts.account_type = 5` — сохраняемое значение типа счёта;
- `AccountViewType::OnlinePayment = 7` — технический код административного просмотра/PDF и параметр `accounts_view.php?account_type=7`;
- `ONLINE_PAYMENT_ACCOUNT_NUMBER = RP18` — текущий префикс отображаемого номера.

`account_type=7` никогда не записывается в `accounts`: он только выбирает обработчик представления. Явное перечисление `AccountViewType` устраняет неоднозначность старых числовых `switch`.

| `AccountViewType` | Код представления | `AccountType` / значение в БД | Префикс |
|---|---:|---|---|
| `Individual` | 1 | `Individual` / 0 | `ACCOUNT_NUMBER` |
| `Abo`, `AboFitness`, `AboLight` | 2, 6, 21 | `Abo` / 1 | `ABO_ACCOUNT_NUMBER` |
| `Special` | 3 | `Special` / 2 | `OTHER_ACCOUNT_NUMBER` |
| `PrivateAccount` | 4 | `PrivateAccount` / 3 | `PREPAYMENT_ACCOUNT_NUMBER` |
| `MembershipFees` | 5 | `MembershipFees` / 4 | `MEMBERSHIP_FEES_ACCOUNT_NUMBER` |
| `OnlinePayment` | 7 | `OnlinePayment` / 5 | `ONLINE_PAYMENT_ACCOUNT_NUMBER` (`RP18`) |

### Точки создания

Счёт формируется только после подтверждения оплаты:

- PayPal: после успешного `DoExpressCheckoutPayment`; используются фактически созданные ID бронирований, PayPal `TOKEN`, `TRANSACTIONID` и ключ профиля;
- Payone: в серверном callback с `txaction=paid`, после создания/нахождения реальных бронирований и успешного обновления их `payment_state`; используются `reference`, `txid`, способ оплаты и ключ профиля.

PayPal `payPerGame()` и Payone `ReservationOrder::insert()` заполняют выходной список ID реально созданных бронирований. Для уже созданных Payone-бронирований используются сохранённые `real_reservation_id`.

Общие операции после подтверждения платежа выполняет `OnlinePaymentPostProcessingService`:

- создаёт реальные бронирования из временных, отправляет календарь и уведомление, снимает временную блокировку;
- создаёт предоплатный счёт и зачисляет сумму пакета на личный счёт;
- выполняет компенсирующее списание и удаляет предоплатный счёт при ошибке шлюза.

Обработчики PayPal и Payone передают сервису только данные своего шлюза и сохраняют специфичное состояние: PayPal — session/NVP, Payone — callback, Redis и собственные статусы ошибок.

`reservation::setPaymentStateReservations()` обновляет временные строки запросом `WHERE reference LIKE ?` с параметром `$reference . '%'`, потому что после callback значение может иметь вид `reference|txid`. Метод выполняет `UPDATE` в режиме без выборки и возвращает `bool`.

### Пошаговый алгоритм создания

`AccountsEngine::createOnlinePaymentInvoiceForReservations()` выполняет следующие проверки и действия:

1. Нормализует и удаляет повторяющиеся ID бронирований. Пустой список завершает обработку без счёта.
2. Проверяет `canCreateOnlinePaymentInvoice()`: функция должна быть включена, а по переданным `sys_reservation_id` ещё не должно быть онлайн-счёта.
3. Требует непустые `paymentReference` и `transactionId`; без подтверждённых реквизитов транзакции счёт не создаётся.
4. Начинает транзакцию БД и загружает все переданные бронирования с `FOR UPDATE`. Если хотя бы одно бронирование отсутствует, создание отменяется.
5. Отбирает оплачиваемые основные строки: `main_reservation_id` пуст, `encash = 3`, `price > 0`.
6. Повторно проверяет существование счёта по `sys_reservation_id` уже под блокировкой, защищаясь от параллельных/повторных callback.
7. Проверяет, что все основные строки относятся к одному зарегистрированному клиенту либо к одному гостю.
8. Создаёт/получает снимок плательщика в `accounts_clients`, генерирует номер, вставляет одну запись `accounts.account_type = 5` и строки `accounts_reservations`.
9. Фиксирует транзакцию. Любая ошибка откатывает только создание счёта и его снимков.

Оплата и уже созданные бронирования не откатываются при ошибке счёта. Ошибка отдельно журналируется каналом `accounts` с ID бронирований и причиной.

### Обычные и групповые бронирования

Для обычного, не открытого бронирования `main_reservation_id` не задан. Если оно оплачено онлайн (`encash = 3`) и имеет положительную цену, оно становится обычной строкой онлайн-счёта. Несколько обычных бронирований одной оплаты и одного плательщика попадают в один счёт отдельными строками.

Для открытых кортов и других связанных групп действуют дополнительные правила:

- общая стоимость хранится в основном бронировании;
- дополнительные бронирования имеют `main_reservation_id` и обычно цену `0`;
- в `accounts_reservations` сохраняется только основное бронирование с положительной ценой;
- дополнительные строки не увеличивают количество позиций счёта, но участвуют в расчёте времени;
- время основной позиции расширяется до `MIN(start)` — `MAX(finish)` по всей переданной группе;
- алгоритм не ограничен двумя получасовыми периодами и поддерживает 2, 3, 4 и больше периодов любой фактической длительности.

### Клиент и гость

Для зарегистрированного клиента все основные строки должны иметь один положительный `client_id`. Актуальные данные клиента копируются в стандартный снимок `accounts_clients`; изменение или удаление профиля позднее не меняет уже сформированный счёт.

Для гостя `client_id` бронирования пустой/нулевой:

- все основные строки должны принадлежать одному гостю по имени и фамилии;
- имя и фамилия берутся прежде всего из сохранённого бронирования;
- email и доступные адресные/контактные данные берутся из снимка плательщика;
- для PayPal данные доступны из пользовательской сессии;
- для асинхронного Payone callback снимок временно сохраняется в Redis под ключом `reference`;
- для каждого отдельного счёта создаётся независимый `accounts_clients` с `sys_client_id = NULL`;
- при чтении онлайн-счёта гость с `sys_client_id = NULL` получает статус членства `no_club_rate` и учитывается как нечлен;
- при создании гостевого онлайн-счёта ставка НДС берётся из настройки по умолчанию `config_nds.set_default = 1` и сохраняется в `accounts.nds`;
- три бронирования одной оплаты создают один счёт и один гостевой снимок; три отдельные оплаты создают три независимых снимка;
- смешивание зарегистрированного клиента и гостя либо разных гостей в одном счёте запрещено.

Payone принимает гостя при формировании запроса, заполняя имя, фамилию и email из гостевой сессии. В техническом `payone_logs` зарегистрированный клиент определяется также из последнего сегмента `portal.param`, а для гостя записывается числовой `client_id = 0`, совместимый со старыми таблицами логов.

### Хранение и независимость от бронирования

Данные распределены по существующим таблицам:

- `accounts` — заголовок, тип `5`, номер, даты, НДС, площадка и `price_info`;
- `accounts_clients` — неизменяемый для этого счёта снимок плательщика;
- `accounts_reservations` — снимки позиций счёта;
- `accounts_reservations.sys_reservation_id` — ID исходного бронирования только для идемпотентности и трассировки.

Просмотр счёта и проверка его существования не делают обязательный `JOIN` к `reservations`. Поэтому удаление исходного бронирования после формирования счёта не удаляет счёт, не ломает PDF и не скрывает его из меню.

### Транзакционные данные в `price_info`

Формат совместим с существующими предоплатными счетами и исторически всегда начинается с `paypal|`:

```text
paypal|reference|transactionId[|paymentType][|tk:rawurlencode(profileTypeKey)]
```

Примеры:

```text
paypal|EC-...|PAYID-...|tk:paypal
paypal|6a566766e3c1f|1456563111|Card|tk:payone
```

- для прямого PayPal `reference` — это `TOKEN`, `transactionId` — `TRANSACTIONID`, сегмента `paymentType` нет;
- для Payone используются `reference`, `txid` и сохранённое название способа оплаты (`Card`, `Paypal`, `Wero`, `BNPL`);
- `tk:` хранит URL-кодированный ключ профиля (`paypal`, `paypal|...`, `payone`, `payone|...`) на момент операции;
- `OnlineGatewayService::parseOnlinePaymentInvoicePriceInfo()` отделяет технический хвост, определяет шлюз по `profileTypeKey` (с fallback по наличию Payone `paymentType`) и возвращает структурированные поля;
- смена primary gateway после оплаты не меняет провайдера в существующем счёте.

### Меню, журнал, архив и PDF

Для каждого активного типа площадки используются общие названия, независимо от выбранного провайдера:

- `Paypal/Payone-Rechnungsjournal` → `accounts.php?action=showOnlinePaymentAccountsList`;
- `Paypal/Payone-Rechnungsarchiv` → `accounts.php?action=showOnlinePaymentAccountsArchives`.

Меню показывается, если функция включена **или** в `accounts` уже существует хотя бы один счёт типа `5`. Поэтому отключение `payment.online_payment_use` либо `account.online_payment_invoice_use`:

- запрещает создание новых онлайн-счетов;
- не скрывает существующие действующие, архивные или аннулированные счета;
- сохраняет возможность открыть и распечатать старый счёт.

Журнал и архив поддерживают фильтры по году и месяцу:

- журнал: `archives = 0`, просмотр, отправка, массовая печать, CSV-выгрузка и перенос в архив;
- архив: `archives = 1`, просмотр, аннулирование и формирование корректирующего документа;
- SEPA-форма не выводится: `sepaForm('other')` относится к специальным счетам и загружает `getOtherAccounts()`, а онлайн-счёт уже оплачен через шлюз и не должен повторно попадать в прямое списание;
- в колонке `Gesamtbetrag` выводится сумма и иконка сохранённого шлюза (`paypal_logo.png` либо `payone.png`), выбранная по разобранному `price_info`;
- если транзакционная строка неполна и не разбирается, сумма остаётся доступной без иконки.

PDF загружается через `AccountViewType::OnlinePayment` и использует только сохранённые снимки. Полная строка `price_info` пользователю не показывается:

- PayPal: `Bezahlung via PayPal`, `PayPal-Token`, `PayPal-Transaktions-ID`;
- Payone: `Bezahlung via Payone`, `Payone-Referenz`, `Payone-Transaktions-ID`, `Zahlungsart`;
- подписи добавлены в административные локализации `de`, `en` и `ru`;
- технический хвост `tk:` остаётся внутренним значением.

### CSV журнала онлайн-счетов

В CSV общего журнала PayPal/Payone (`downloadOnlinePaymentAccounts`) после существующих 17 столбцов добавлены:

- `Tag der Buchung/ Bezahlung` — дата выставления счёта: `accounts.date_creation`, при отсутствии — `accounts.date_start`, как в PDF.
- `Tag der Belegung/ Nutzung` — уникальные даты игр из снимков `accounts_reservations.date`, по возрастанию через запятую в одной ячейке.
- `PayPal Transaktions-ID` — идентификатор только прямой PayPal-транзакции. Для Payone ячейка остаётся пустой,
  включая оплату способом PayPal через Payone.

Даты заполняются для обоих провайдеров в формате `d.m.Y`. При отсутствии позиций или идентификатора соответствующая ячейка пустая.
На счёт остаётся одна строка. Банковские столбцы, суммы и состав выгружаемых счетов сохранены; другие журналы не затронуты.
Позиции загружаются существующим `getOnlinePaymentAccountsById()` одним запросом для всех счетов, независимо от текущих бронирований.
Шлюз и транзакция определяются через `OnlineGatewayService::parseOnlinePaymentInvoicePriceInfo()`;
token, reference и технический хвост `tk:` в новые столбцы не попадают. Заголовки переведены на DE/EN/RU.

`OnlinePaymentInvoiceCsvTest` (группа `accounts-online-payment-csv`) проверяет даты, их сортировку и уникальность,
сохранение одной строки на счёт, банковских полей и сумм, переводы, пустые значения и различение PayPal/Payone.
Общие проверки включаются capability `accounts.online-payment-invoice-csv`, проверки общего журнала —
`accounts.online-payment-invoice-csv-gateways`.

## Хранение настроек в БД (`config`)

### 1) Основная ветка (primary) и включение онлайн‑оплаты

Тип `payment`:

- `payment.online_payment_use` — включение онлайн‑оплаты;
- `payment.online_gateway_primary` — основной провайдер: `paypal` | `payone`.

### 2) Профили PayPal (контекстные)

Профили PayPal хранятся в `config` в типах:

- `paypal` (дефолт)
- `paypal|...` (контекстные варианты по типу площадки / спорту)

Основные поля профиля: `api_username`, `api_password`, `api_signature`, `paypal_use`.

Важно: для работоспособной PayPal NVP‑интеграции **обязательны все три реквизита** (`api_username`, `api_password`, `api_signature`). Если хотя бы одно пустое — профиль считается неактивным для рантайма.


### 3) Профили Payone (контекстные)

Профили Payone хранятся в `config` в типах:

- `payone` (дефолт)
- `payone|...` (контекстные варианты по типу площадки / спорту)

Из БД переопределяются **только**:

- `mid`, `aid`, `portalid`, `key`, `payone_use`

Остальные параметры Payone (например `mode`, `encoding`, `api_version`, `useUrlCreation`, `param`) остаются из `pay.config`.

Поддерживаемые способы оплаты Payone (через `payone_methods` в профиле):

- `cc` — карта
- `pp` — PayPal (wallet внутри Payone)
- `wero` — Wero (wallet внутри Payone)
- `bnpl` — BNPL (через financing)

Доп. параметры методов Payone:

- `payone_method_params` (JSON) — контейнер для параметров, которые нужны только отдельным методам.
  - Для `bnpl` (PDD) используются ключи:
    - `bnpl.df_partner_id`
    - `bnpl.df_merchant_id` — больше не требуется: merchant id берётся из данных Payone (mid).
  - Если `bnpl` включён в `payone_methods`, но эти значения не заполнены — метод `bnpl` **не показывается** в UI и **не принимается** сервером.
  - Для `bnpl` (PDD) также обязателен device fingerprinting (Payla DCS):
    - на странице оформления (заказ / пополнение) подключается Payla DCS сниппет;
    - с фронта отправляется hidden-поле `device_token`;
    - в запрос Payone передаётся `add_paydata[device_token]`;
    - если `bnpl` выбран, но `device_token` пустой — запрос отклоняется на сервере.
  - Для `bnpl` (PDD) также обязательны данные пользователя (проверяются сервером при выборе метода):
    - телефон (`telephonenumber`) — берётся из профиля клиента (`phone_mobile` → `phone`)
    - дата рождения (`birthday`) — формат `YYYYMMDD` (нормализуется из `clients.birthday`)
    - email
    - IP (`Service::request()->getIPAddress()`)
    - держатель счёта (`bankaccountholder`) — из `clients.account_owner` (fallback: имя+фамилия)
    - IBAN (`iban`) — из `clients.bank_iban`
    - `customer_is_present=yes`
    - `businessrelation=b2c`


## Выбор провайдера в рантайме

Единая точка выбора:

- `AC\core\modules\payment\services\OnlineGatewayService`
  - `primaryGateway()` — выбранный админом primary из БД (или legacy‑fallback);
  - `effectivePrimaryForRuntime()` — фактический провайдер для рантайма:
    - `paypal` / `payone` — когда выбранная ветка работоспособна;
    - `none` — когда online‑оплата включена, но выбранный `payone` не подтверждён для текущего контекста (профиль/реквизиты/методы оплаты).

`PaymentConfig` использует `effectivePrimaryForRuntime()` для показа/использования PayPal/Payone.

## Фиксация профиля на момент оплаты (шаг 6)

Чтобы после смены **primary** в админке старые операции не «перекрашивались» под текущий провайдер:

- **Бронь:** в `paypal_status` пишется ключ профиля в том же смысле, что и `config.type` (`paypal` / `paypal|…` / `payone` / `payone|…`), см. `OnlineGatewayService::onlinePaymentProfileTypeKey()` и вставку в `ReservationsTable` / `Engines::insertReservation`.
- **Временные брони PayPal NVP:** в `reference` — TOKEN, затем `TOKEN|TRANSACTIONID`.
- **Предоплатные счета (пополнение Guthaben):** в `accounts.price_info` — цепочка платежа (как раньше, с префиксом `paypal|` для совместимости) плюс хвост **`|tk:…`** с `rawurlencode(typeKey)` для дефолтного профиля на момент оплаты (`OnlineGatewayService::encodePrepaymentPriceInfoTypeKeyTail()`, разбор — `parseTypeKeyFromPrepaymentPriceInfo()`).
- **Счета онлайн-оплаты бронирований:** в `accounts.price_info` сохраняется такая же цепочка платежа: `paypal|reference|transactionId[|payType]|tk:…`. Для PayPal используются TOKEN и TRANSACTIONID, для Payone — reference, txid и способ оплаты.
- **PDF онлайн-счёта:** техническая строка `price_info` напрямую не выводится. Для PayPal показываются `TOKEN` и `TRANSACTIONID`, для Payone — `reference`, `txid` и способ оплаты. Хвост профиля `tk:` остаётся внутренним значением.
- **Отчёты:** иконка провайдера по сохранённому `paypal_status` или по ключу из `price_info` для строк пополнения.

Подробный чеклист и оговорки по шагу 6 — в `online-gateway-implementation-plan.md` (раздел «Шаг 6»).

## Поведение UI (сайт / touch / пополнение)

- На сайте и touchscreen `PaymentMethodResolver` автоматически выбирает личный счёт (`GH`) для зарегистрированного клиента
  с `encash = 2` независимо от баланса и стоимости бронирования, если способ не скрыт и не выбран другой доступный
  `DEFAULT_PAYMENT_METHOD`. Проверка достаточности средств при оформлении бронирования сохраняется.
- Формы бронирования показывают онлайн‑оплату через `PaymentConfig::showPaypalPaymentMethod()` / `showPayonePaymentMethod()` (в зависимости от primary).
- Пополнение счёта (`prepayment.php`) выбирает ветку через `OnlineGatewayService::effectivePrimaryForRuntime()`.
