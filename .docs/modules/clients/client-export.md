# CSV-экспорт клиентов

## Текущая реализация

Cron-действие `deployClient` реализовано в `app/cron/Cron.php`. Оно получает
весь список клиентов, для каждого клиента определяет последнюю и следующую
бронь, собирает CSV в строке, сохраняет временный файл и отправляет его через
`DeployFile::deploy()`.

Имя файла имеет вид:

```text
export-{court}_YYYY-MM-DD_HH-mm-ss.csv
```

Поскольку имя содержит время формирования, каждый запуск создаёт новый
удалённый файл. Текущий путь использует `uploadFile()` и не скачивает
предыдущий экспорт для сравнения содержимого.

На небольших клиентских базах такой процесс допустим. Например, экспорт из
1 846 строк занимает около 217 КБ. При сохранении среднего размера строки
экспорт 500 000 клиентов будет занимать примерно 57–70 МБ на диске.

## Ограничения текущего процесса

Размер готового CSV не отражает полный расход памяти. Одновременно могут
существовать:

- весь результат выборки клиентов в виде PHP-массивов;
- строка со всем CSV;
- вторая строка с BOM и готовым содержимым;
- промежуточные данные и временные копии строк.

PHP-массивы имеют значительные накладные расходы, поэтому 500 000 клиентов
могут потребовать от сотен мегабайт до нескольких гигабайт памяти. При
обычном `memory_limit` процесс может завершиться до формирования файла.

Дополнительно текущий цикл вызывает получение последней и следующей брони
отдельно для каждого клиента. На 500 000 клиентов это создаёт до 500 000
дополнительных SQL-запросов и становится основным ограничением времени.

## Планируемое масштабирование

### Поток данных

1. Открыть временный файл в бинарном режиме.
2. Записать UTF-8 BOM и строку заголовков.
3. Читать клиентов порциями, используя устойчивую пагинацию
   `client_id > last_client_id ORDER BY client_id LIMIT :limit`.
4. Для идентификаторов текущей порции одним пакетным запросом получить
   последнюю и следующую бронь.
5. Последовательно записать строки через `fputcsv()` с разделителем `;`.
6. После успешного закрытия файла передать его существующему
   `DeployFile::deploy()`.
7. Удалять локальный файл только после подтверждённой доставки.

Начальный размер порции — 2 000 клиентов. Итоговое значение следует выбрать
по измерениям на рабочей базе. Пагинация через `OFFSET` для полного экспорта
не рекомендуется: с ростом смещения она замедляется и хуже переносит
изменения данных во время выполнения.

### Доставка и восстановление

FTP/SFTP-загрузка локального файла уже выполняется потоково, поэтому её не
нужно заменять передачей строкового содержимого. Для предотвращения появления
частично загруженного конечного файла следует рассмотреть отправку под
временным именем с последующим `rename()`.

Необходимо определить и зафиксировать:

- запрет или блокировку параллельных запусков одного экспорта;
- срок хранения локальных файлов после ошибки;
- очистку старых удалённых экспортов;
- допустимость полного перезапуска после сбоя либо контрольную точку по
  последнему обработанному `client_id`;
- итоговое логирование количества прочитанных, отфильтрованных и записанных
  клиентов, размера файла, времени SQL, генерации и доставки.

Хеширование удалённого содержимого не является основной оптимизацией для
этого процесса: файл с временной меткой создаётся заново. Если в будущем
появится фиксированное удалённое имя, проверку неизменности следует строить на
сохранённом хеше или отдельном hash-файле без обратного скачивания большого CSV.

## Критерии приёмки

- экспорт не загружает в память полный список клиентов и полный CSV;
- пиковая память практически не зависит от общего числа клиентов;
- отсутствует SQL-запрос последней/следующей брони на каждую отдельную запись;
- значения с `;`, кавычками и переносами строк формируют корректный CSV;
- тестовый экспорт не менее 500 000 клиентов завершается в установленный
  лимит времени и памяти;
- при ошибке доставки локальный файл сохраняется, а конечный удалённый файл
  не остаётся частично обновлённым;
- повторный или параллельный запуск имеет явно определённое поведение.
