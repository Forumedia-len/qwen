# Личный счёт клиента и снимки баланса

## Назначение

Личный счёт клиента хранит доступную сумму в поле `clients.prepayment_sum`.
Таблица `private_account_transactions` содержит журнал приходов и расходов,
их статусы, источник операции и связанные данные.

При успешном выполнении операции система дополнительно сохраняет в
`private_account_transactions.related_data` два снимка:

- `balance_before` — сумма на личном счёте непосредственно перед операцией;
- `balance_after` — сумма на личном счёте после операции.

Снимки позволяют восстанавливать последовательность изменения счёта без
расчёта баланса по всей предыдущей истории. Они не являются отдельным балансом:
актуальным значением остаётся `clients.prepayment_sum`.

## Модель данных

### Текущий баланс

```text
clients.prepayment_sum DOUBLE(10,2)
```

### Журнал операций

Основные поля `private_account_transactions`:

| Поле | Назначение |
|---|---|
| `id` | Внутренний идентификатор операции |
| `client_id` | Клиент, чей баланс изменяется |
| `type_direction` | `in` — приход, `out` — расход |
| `type_code` | Бизнес-причина операции |
| `amount` | Положительная сумма операции |
| `related_data` | Дополнительные данные в JSON, включая снимки баланса |
| `related_id` | Идентификатор связанной сущности |
| `status` | Состояние операции |
| `external_id` | Внешний или идемпотентный идентификатор |

Сумма хранится положительной. Знак изменения определяется полем
`type_direction`.

## Формат снимков

Пополнение на 25 при исходном балансе 100:

```json
{
  "source": "bank_transfer",
  "balance_before": 100.0,
  "balance_after": 125.0
}
```

Списание 40 при исходном балансе 100:

```json
{
  "reservation_id": 123,
  "balance_before": 100.0,
  "balance_after": 60.0
}
```

Снимки добавляются к уже переданному при создании операции `related_data`.
Другие ключи не удаляются. Если при создании операции вызывающий код передал
собственные `balance_before` или `balance_after`, при успешном выполнении они
заменяются значениями, прочитанными из БД.

Значения округляются до двух знаков и сохраняются как числа JSON, а не строки.

## Направления и статусы

### Направления

| Направление | Действие с балансом |
|---|---|
| `in` | `prepayment_sum + amount` |
| `out` | `prepayment_sum - amount` |

Перед расходом проверяется достаточность средств.

### Статусы

| Статус | Значение | Влияние на баланс |
|---|---|---|
| `pending` | Операция создана и ожидает выполнения | Не изменяет |
| `succeeded` | Операция успешно выполнена | Изменяет один раз |
| `cancelled` | Отменена до выполнения | Не изменяет |
| `failed` | Завершилась ошибкой | Не изменяет |
| `reversed` | Успешная операция отменена компенсирующей операцией | Исходная операция напрямую баланс не меняет повторно |

Допустимые переходы:

```text
pending ──→ succeeded
pending ──→ cancelled
pending ──→ failed
succeeded ──→ reversed
```

Снимки создаются при переходе `pending → succeeded`, потому что только этот
переход применяет приход или расход к `clients.prepayment_sum`.

## Варианты выполнения

### Синхронный приход или расход

Методы modComm `PrivateAccount/deposit` и `PrivateAccount/withdraw` выполняют
полный цикл в одном вызове:

```text
modComm-запрос
  → PrivateAccountController::sendTransaction()
  → PrivateAccountTransactionDto::forCreate()
  → addDeposit() / addWithdraw()
  → INSERT операции со статусом pending
  → succeeded()
  → изменение баланса и сохранение снимков
  → status = succeeded
```

### Отложенная операция

Методы `PrivateAccount/addDeposit` и `PrivateAccount/addWithdraw` только создают
`pending`-операцию. Позже вызывается `PrivateAccount/changeStatus`.

Бронирование с оплатой личным счётом использует отложенный расход:

```text
requestPayment()
  → PrivateAccount/addWithdraw
  → pending
  → вставка бронирования
  → makePayment()
  → PrivateAccount/changeStatus(status = succeeded, relatedId = reservation_id)
  → списание и снимки баланса
```

Если бронирование не вставлено, операция переводится в `failed`, а баланс не
изменяется.

## Источники операций

Текущие бизнес-сценарии включают:

- оплату бронирования личным счётом;
- возврат после удаления бронирования;
- возврат после удаления дня абонемента;
- пополнение через PayPal или Payone;
- компенсирующее списание при отмене онлайн-пополнения;
- прямые внутренние вызовы `deposit`, `withdraw` и `changeStatus`.

`type_code` уточняет причину. Примеры используемых значений:

- `reservation_created_private_account`;
- `reservation_removed_private_account`;
- `reservation_removed_paypal`;
- `reservation_removed_payone`;
- `ticket_removed`;
- `paypal_deposit`;
- `paypal_deposit_removed`.

Payone сейчас сохраняет совместимые коды `paypal_deposit` и
`paypal_deposit_removed`. Административное представление заменяет префикс на
`payone` при включённой конфигурации Payone.

## Выполнение успешной операции

`PrivateAccountTransactionEngine::succeedTransaction()` выполняет следующие
действия:

1. Проверяет наличие внешней БД-транзакции.
2. Начинает собственную транзакцию либо создаёт `SAVEPOINT`.
3. Загружает строку операции с `FOR UPDATE`.
4. Повторно проверяет переход `pending → succeeded` под блокировкой.
5. Загружает строку клиента с `FOR UPDATE`.
6. Сохраняет текущий `prepayment_sum` как `balance_before`.
7. Выполняет приход или расход через существующий `ClientsEngine`.
8. Повторно читает `prepayment_sum` как `balance_after`.
9. Объединяет снимки с `related_data`.
10. Одним запросом сохраняет `related_data` и статус `succeeded`.
11. Выполняет `COMMIT` либо освобождает `SAVEPOINT`.

При ошибке выполняется `ROLLBACK` или `ROLLBACK TO SAVEPOINT`, а внутренняя
диагностика записывается в журнал `private_account`.

## Параллельные операции и движки таблиц

Описанная транзакционная схема даёт полные гарантии, когда обе задействованные
таблицы используют транзакционный движок с блокировками строк. В эталонной схеме
проекта обе таблицы используют InnoDB:

```text
clients                         InnoDB
private_account_transactions    InnoDB
```

При этой схеме:

- `SELECT ... FOR UPDATE` блокирует конкретную операцию и строку клиента;
- параллельные изменения одного счёта выполняются последовательно;
- `ROLLBACK` отменяет и изменение `clients.prepayment_sum`, и изменение журнала;
- снимки и статус фиксируются вместе с изменением баланса.

На старых сайтах таблица `clients` могла сохраниться с движком MyISAM. MyISAM не
участвует в `COMMIT`, `ROLLBACK` и `SAVEPOINT` как InnoDB и не даёт строковую
блокировку, ожидаемую от `SELECT ... FOR UPDATE`. Для такого сайта полная
атомарность и точность снимков под параллельной нагрузкой не гарантируются до
миграции таблицы.

### Проверка реальной БД

SQL-файлы описывают эталон проекта, но конкретный сайт мог быть мигрирован
отдельно. Движки фактических таблиц нужно проверить:

```sql
SELECT TABLE_NAME, ENGINE
FROM information_schema.TABLES
WHERE TABLE_SCHEMA = DATABASE()
  AND TABLE_NAME IN (
    '{prefix}clients',
    '{prefix}private_account_transactions'
  );
```

Для полных гарантий обе строки должны содержать `InnoDB`.

### Миграция старого сайта

Если проверка обнаружила MyISAM, целевое изменение:

```sql
ALTER TABLE `{prefix}clients` ENGINE = InnoDB;
```

Для эталонной схемы и уже обновлённых сайтов изменение не требуется. Код личного
счёта не выполняет миграцию автоматически. Перед обновлением старого сайта
необходимо проверить размер таблицы, время блокировки, резервное копирование,
индексы и совместимость существующих запросов.

## Чтение снимков

Снимки возвращаются внутри `related_data` методами:

- `PrivateAccount/transactions`;
- `PrivateAccount/transaction`;
- `PrivateAccount/listIn`;
- `PrivateAccount/listOut`.

DTO декодирует JSON в массив:

```php
$before = $transaction->related_data['balance_before'] ?? null;
$after  = $transaction->related_data['balance_after'] ?? null;
```

Административная история личного счёта сейчас использует `related_data` для
комментариев к операциям, но отдельно снимки баланса не выводит. Время создания
строки отображается с секундами в формате `DD.MM.YYYY HH:MM:SS`; время самой
брони в комментарии сохраняет прежний формат без секунд.

## Предполагаемые обновления

Краткая карточка для поиска и планирования реализации:
[CLIENTS-001](../../improvements/private-account-balance-fields.md).

Текущее хранение снимков в `related_data` является совместимым промежуточным
решением. Целевая модель должна хранить обязательные финансовые данные в
отдельных типизированных полях, а `related_data` использовать только для
необязательного контекста: идентификатора бронирования, платёжного провайдера,
комментария и других данных, состав которых зависит от типа операции.

### Целевая схема

Для журнала операций предполагается добавить два nullable-поля:

```sql
ALTER TABLE `{prefix}private_account_transactions`
  ADD `balance_before` DECIMAL(12,2) DEFAULT NULL AFTER `amount`,
  ADD `balance_after` DECIMAL(12,2) DEFAULT NULL AFTER `balance_before`;
```

`NULL` сохраняет корректную семантику для операций, которые не изменили счёт:
`pending`, `failed` и `cancelled`. Оба значения заполняются только при успешном
переходе `pending → succeeded`.

Текущий баланс клиента также предполагается перевести с приближённого типа
`DOUBLE` на точный десятичный тип:

```sql
ALTER TABLE `{prefix}clients`
  MODIFY `prepayment_sum` DECIMAL(12,2) DEFAULT 0.00;
```

На первом этапе миграция сохраняет существующую nullable-семантику поля.
Добавление `NOT NULL` допустимо отдельным изменением только после проверки и
нормализации существующих `NULL`-значений.

Индексы для `balance_before` и `balance_after` по умолчанию не требуются. Их
следует добавлять только при появлении реальных запросов с фильтрацией или
сортировкой по снимкам.

### Задачи миграции

Переход следует выполнять поэтапно, чтобы старый и новый код могли временно
работать с одной базой:

1. Проверить реальные схемы всех сайтов: тип `prepayment_sum`, движки таблиц,
   диапазон значений, наличие `NULL`, некорректного JSON и снимков в
   `related_data`. Подготовить резервную копию и оценить время блокировки
   `ALTER TABLE`.
2. Добавить nullable-поля `balance_before` и `balance_after` в журнал. Это
   расширение не меняет поведение действующего кода.
3. Обновить SQL-эталон, модель таблицы, DTO и сериализацию API. Для денежных
   значений не выполнять промежуточные вычисления через `float`: использовать
   десятичные строки либо общий денежный value object проекта.
4. Изменить `succeedTransaction()`: записывать отдельные снимки тем же запросом,
   которым устанавливается `status = 'succeeded'`, внутри существующей
   БД-транзакции и под теми же блокировками `FOR UPDATE`.
5. На период совместимости выполнять двойную запись снимков в новые поля и в
   `related_data`. При чтении сначала использовать отдельные поля, а при их
   `NULL` — старые JSON-ключи.
6. Перенести исторические значения из `related_data` в новые поля. Обновлять
   только строки с валидным JSON, двумя числовыми значениями и пустыми целевыми
   полями; спорные строки вынести в отчёт и не исправлять автоматически.
7. Сверить миграцию: количество перенесённых строк, диапазоны сумм, соответствие
   JSON и колонок, а также цепочки `balance_after → balance_before` для
   последовательных успешных операций одного клиента.
8. Переключить административную историю, modComm и остальные потребители на
   отдельные поля. После обновления всех сайтов прекратить двойную запись и
   удалить системные ключи баланса из нового `related_data`. Старые ключи можно
   оставить в исторических строках либо удалить отдельной необязательной
   очисткой.
9. Отдельно преобразовать `clients.prepayment_sum` в `DECIMAL(12,2)`. До и после
   `ALTER TABLE` сравнить число строк, `NULL`-значения, минимумы, максимумы и
   контрольные суммы округлённых значений.

Миграцию `prepayment_sum` не следует объединять с переносом снимков в один
неразделимый релиз: у изменений разные риски и разные варианты отката.

### Задачи изменения процесса

После подготовки схемы необходимо:

- считать `balance_before` и `balance_after` системными полями, которые нельзя
  принимать из пользовательского или внешнего запроса;
- сохранять оба снимка и статус `succeeded` атомарно вместе с изменением
  `clients.prepayment_sum`;
- не заполнять снимки для `pending`, `failed` и `cancelled`;
- защитить отдельные поля от последующего изменения через `changeRelated()`;
- добавить снимки в DTO и ответы API без удаления существующего
  `related_data`;
- проверить правила возврата и `reversed`: компенсирующая операция должна иметь
  собственные снимки, а исходная успешная операция — оставаться неизменной;
- добавить интеграционные тесты на старую запись только с JSON, новую запись с
  колонками, период двойной записи, конкурентные операции и откат транзакции.

После завершения перехода отдельные поля становятся единственным источником
снимков, `clients.prepayment_sum` остаётся источником текущего баланса, а
`related_data` содержит только дополнительный контекст операции.

## Известные ограничения процесса

1. При синхронном `deposit` или `withdraw` запись `pending` создаётся до начала
   транзакционного участка изменения баланса. При неуспехе может сохраниться
   `pending` для последующего анализа или обработки.
2. `ReservationsModel::insertReservation()` сейчас не учитывает возвращаемое
   значение `makePayment()` после вставки бронирования. Возможна вставленная
   бронь при неуспешном завершении списания.
3. `reversed()` сначала меняет статус исходной операции, а затем создаёт
   компенсирующую. Эти действия пока не объединены в одну транзакцию.
4. Ролевые правила modComm объявлены, но базовая авторизация контроллера сейчас
   фактически разрешает вызов. Нельзя считать modComm самостоятельной границей
   безопасности до отдельного исправления.
5. После успешного `changeStatus` контроллер отдельно вызывает `changeRelated()`.
   Переданный на этом этапе `relatedData` технически может перезаписать
   `balance_before` и `balance_after`. Эти ключи должны считаться системными и
   не передаваться вызывающим кодом до добавления отдельной защиты в движке.
   Переход на отдельные поля, описанный в предполагаемых обновлениях, устранит
   эту возможность для новых снимков.

Эти ограничения существовали в бизнес-процессе независимо от добавления
снимков баланса и должны устраняться отдельными изменениями.

## Проверка изменений

Минимальные сценарии для интеграционного тестирования:

1. Приход: `100 → 125`, снимки `100/125`.
2. Расход: `125 → 75`, снимки `125/75`.
3. Недостаточно средств: баланс не меняется, статус не становится `succeeded`.
4. Ошибка сохранения журнала: баланс и журнал откатываются при обеих таблицах
   InnoDB.
5. Два параллельных прихода: снимки образуют последовательную цепочку.
6. Два параллельных расхода: нельзя списать больше доступного баланса.
7. Отложенная операция бронирования: `pending → succeeded` получает снимки.
8. `failed` и `cancelled` не получают снимков и не меняют баланс.
