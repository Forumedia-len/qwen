# Создание абонемента и связь с блокировками и праздниками

## Общая модель

В коде абонемент называется `ticket`. Он представляет собой правило
повторения, а не набор отдельных бронирований:

- клиент и площадка;
- время начала и окончания;
- выбранные дни недели;
- периодичность `space` — каждую неделю или раз в N недель;
- скидка и комментарий;
- один или несколько диапазонов действия.

Основная запись хранится в `tickets`, диапазоны действия — в
`tickets_periods`. Поэтому отсутствие отдельных строк в `reservations` для
каждой игры абонемента является штатным поведением.

## Точка входа

Административное меню в текущей конфигурации ведёт в legacy-интерфейс
`at/tickets.php`. Действие `insertTicket` вызывает одноимённый метод
`tickets_admin::insertTicket()` и после обработки обновляет экспортируемый
календарь iCal/WebIO.

В `core/modules/tickets/controllers/admin/TicketsController.php` существует
модульная реализация с аналогичным общим потоком, но текущая структура
административного меню использует `tickets.php`.

## Последовательность создания

### 1. Чтение данных формы

Администратор задаёт:

- `area_id` — площадку;
- `client_id` — клиента;
- `time_start` и `time_finish`;
- `weekdays` — дни недели;
- `space` — периодичность по неделям;
- даты начала и окончания;
- скидку `discount`;
- комментарий `title`.

Значение окончания `24:00` приводится к формату, используемому движком, через
`TimeHelper::convertTime24()`.

### 2. Проверка и создание основной записи

`reservation_tickets::insertTicket()` вызывает `checkInsertTicket()` и
проверяет:

1. Существует ли выбранная площадка.
2. Существует ли клиент с режимом `1` или `2`.
3. Соответствуют ли оба времени формату `H:i`.
4. Находится ли время начала раньше времени окончания.
5. Выбран ли хотя бы один день недели.

После успешной проверки создаётся строка `tickets`. Вместе с данными формы
сохраняются:

- `period_start` и `period_finish`;
- `week_begin = WEEK(period_start, 3)` — базовая ISO-неделя для расчёта
  периодичности;
- даты создания и изменения.

### 3. Добавление диапазона действия

После создания основной записи контроллер вызывает
`reservation_tickets::addPeriodToTicket()`. Этот же метод используется при
ручном добавлении диапазона к существующему абонементу. Клонирование на новый
сезон создаёт новый абонемент и также проходит через этот стандартный метод.

Метод:

- вычитает уже существующие диапазоны абонемента и обрабатывает только
  фактически добавляемые даты;
- получает обычные, периодические и бессрочные блокировки площадки;
- формирует реальные игровые даты с учётом `weekdays`, `space`, `week_begin`
  и `ABO14_TYPE`;
- исключает любой слот, имеющий ненулевое пересечение с блокировкой;
- вырезает полностью закрытые игровые даты из `tickets_periods`;
- сохраняет частично закрытые слоты в `tickets_disabled_time` с `price = 0`;
  при наличии поля добавляет `source_type = 2` (`initial_block`);
- проверяет одиночные бронирования и другие абонементы уже по оставшейся
  структуре;
- связывает существующие исключения внутри сохранённого диапазона с периодом
  по `ticket_id` и `disabled_date`, не полагаясь на потенциально устаревший
  `tickets_disabled_time.period_id`;
- при ошибке записи компенсирующе восстанавливает прежние `tickets_periods` и
  связи `tickets_disabled_time`.

Опорные первые игровые даты определяют фазу повторения, но не ограничивают
диапазон снизу. `CalendarHelper::getWorkDaysByPeriod()` выравнивает генерацию
шагами `space` недель как вперёд, так и назад от опорных дат. Поэтому период,
добавленный раньше исходного `period_start`, получает игровые даты в той же
фазе недельного или двухнедельного цикла. Это же правило используется
потребителями helper, включая отчёты с фильтрацией по `tickets_periods`.
Значение `space` должно быть положительным целым числом; целочисленная строка
из БД нормализуется, а дробные, нулевые и отрицательные значения отклоняются.

После разрезания поддерживается диапазон `start = finish`, если единственная
дата является игровым днём. Остаточные диапазоны, полученные после вычитания
уже сохранённых периодов, не добавляются, если в них нет ни одной игровой даты
с учётом `weekdays`, `space` и исходной фазы повторения. Если блокировки закрыли
все игровые даты добавляемого диапазона, операция отклоняется.

При ошибке начального добавления контроллер дополнительно удаляет только что
созданную строку `tickets`. При ошибке ручного продления существующий абонемент
и его прежние периоды остаются без изменений.

### 4. Проверка одиночных бронирований

`checkAddPeriodToTicketByReservations()` выбирает пересекающиеся строки
`reservations` для той же площадки и сопоставляет их с реальными активными
слотами добавляемого периода. Полностью вырезанные даты и частичные
`initial_block`-исключения в конфликт не попадают.

При пересечении создание диапазона отклоняется с кодом ошибки `3` и
пользователю показываются занятые даты.

### 5. Проверка других абонементов

`checkAddPeriodToTicketByOtherTickets()` сначала отбирает потенциально
пересекающиеся абонементы по:

- диапазону дат;
- дням недели;
- времени;
- площадке и группе типа площадки.

Затем для обоих абонементов формируются реальные игровые даты и временные
слоты. Это позволяет учитывать периодичность `space`: два абонемента на одном
времени допустимы, если их активные недели не совпадают.

При фактическом пересечении создание диапазона отклоняется с кодом ошибки `4`.
Сообщение содержит клиента, дату и пересекающийся интервал.

### 6. Ошибка и откат

Если любой период или исключение не удалось записать, движок восстанавливает
снимок периодов и связей исключений, существовавший до вызова. Для нового
абонемента контроллер после этого удаляет строку `tickets`. Это компенсирующий
откат, потому что текущие таблицы MyISAM не поддерживают транзакционный
rollback.

Только после полного успеха контроллер сохраняет выбранные даты в cookies
формы и обновляет iCal/WebIO.

## Связь с блокировками

### При добавлении периода абонемента

При создании, ручном продлении и клонировании абонемента учитываются `blocks`
и обе разновидности `blocks_periodical`. Блокировка на неигровую дату не
меняет структуру.

Для площадочной сетки действует правило: если интервалы блокировки и слота
пересекаются хотя бы на одну секунду, исключается весь слот. Несколько
блокировок одного дня рассматриваются совместно. Если они закрывают все слоты
абонемента, дата вырезается из диапазонов; иначе исключённые старты слотов
сохраняются в `tickets_disabled_time`.

Изменение или удаление блокировки после добавления периода не восстанавливает
вырезанные даты и слоты. Повторное добавление перекрывающегося диапазона не
пересчитывает даты, уже входившие в абонемент.

### При построении расписания

В `reservation::getPeriodsByAreasTypeDate()` блокировки и абонементы
загружаются независимо. Для одного слота могут одновременно быть установлены:

- признак блокировки;
- признак абонемента и данные его клиента.

При этом блокировка делает слот недоступным. Для новых абонементов исходное
пересечение также уже закреплено в периодах или исключениях.

### При расчёте игровых часов

`reservation_tickets::getTicketFullDataWithPeriodsAndPriceById()` получает
пересекающиеся блокировки через
`reservation_blocks::checkAreaDateTimePeriodsBlocked()` и передаёт их в
`CalendarHelper::getCountWeekDays()`.

Помощник строит временные слоты блокировки и обнуляет совпавшие слоты
абонемента. Поэтому заблокированные часы не учитываются как игровые часы при
активном legacy-расчёте абонемента.

### Если блокировка создаётся после абонемента

Legacy-интерфейс `at/blocks.php` вызывает
`obtainIntersectionWithAllSourcesForInterval()` и показывает предупреждение о
найденном абонементе. Однако наличие абонемента само по себе не останавливает
создание блокировки: после формирования предупреждения метод вставки
блокировки всё равно вызывается.

Итог: блокировку по-прежнему можно создать поверх существующего абонемента.
Эта операция не переписывает уже сохранённую исходную структуру абонемента.

## Источники исключений и совместимость схемы

`tickets_disabled_time.source_type` использует значения:

- `1` — `cancellation`, обычная отмена;
- `2` — `initial_block`, блокировка при добавлении периода;
- `3` — `manual`, резерв ручного системного исключения.

Неизвестное числовое значение источника не прерывает сохранение и
нормализуется в `cancellation`.

Расписание, проверка занятости, калькуляция и отчёт фактических часов учитывают
все значения. История отмен клиента всегда показывает только строки с
`price > 0` и при наличии поля дополнительно фильтруется по `source_type = 1`.
На БД без поля существующие и новые строки исключений читаются как обычные
отмены. Добавление периода и запись частично заблокированного времени остаются
доступными, но распределение по типам появляется только после добавления
`source_type`. INSERT включает колонку `source_type` только при её наличии.

## Связь с праздниками

### Обычный нерабочий праздник

Обычный праздник хранится с `holidays.sunday = 0`.

`reservation::getPeriodsByAreasTypeDate()` проверяет такой праздник до
построения расписания. В этот день расписание площадок не формируется, поэтому
абонемент:

- остаётся в `tickets` и `tickets_periods`;
- не занимает слоты праздничного дня;
- не учитывается как проведённая игра этого дня.

При legacy-расчёте праздничные даты также преобразуются в полнодневные
интервалы и передаются в `CalendarHelper::getCountWeekDays()` вместе с
блокировками.

### Праздник как воскресенье

Если включены воскресные параметры, праздник хранится с `sunday = 1`. Такой
день не считается полностью закрытым методом `checkHoliday()`, поэтому сам по
себе не выключает абонемент.

Абонемент отбирается по фактическому дню недели даты. Общий движок
ценообразования умеет переключать праздничную цену на воскресную, однако
`reservation_tickets::getPriceTicketByDateTime()` получает цену через
`AreaDto::getPriceByDateTime()`, где используется фактический день недели.
Следовательно, воскресную цену для собственного расчёта абонемента необходимо
учитывать как отдельную точку проверки при изменении логики цен.

## Проверка событий при создании праздника

Контроллер праздников поддерживает обратную проверку: если
`CHECK_BLOCKING_EVENTS_FOR_HOLIDAYS = true`, перед созданием праздника вызывается
`obtainIntersectionWithAllSourcesForIntervalForAllAreas()` на полный день.

Праздник не создаётся, если найдены:

- обычные, периодические или бессрочные блокировки;
- одиночные бронирования;
- абонементы.

В текущем `app/uses/holidays.php` установлено:

```php
HOLIDAY_LIKE_SUNDAY = true;
CHECK_BLOCKING_EVENTS_FOR_HOLIDAYS = false;
HOLIDAY_SUNDAY_TIMES = false;
```

Поэтому в текущей конфигурации праздник можно добавить поверх существующих
абонементов, бронирований и блокировок. Если включить
`CHECK_BLOCKING_EVENTS_FOR_HOLIDAYS`, такое добавление будет запрещено.

## Краткая таблица поведения

| Источник пересечения | Проверка при добавлении периода | Поведение после добавления |
|---|---|---|
| Одиночное бронирование | Добавление запрещается | Не должно пересекаться с абонементом |
| Другой абонемент | Добавление запрещается при совпадении реальных дат и времени | Непересекающиеся недели допустимы |
| Обычная блокировка | Полный день вырезается, частичные слоты сохраняются как `initial_block` | Исключение остаётся частью исходной структуры |
| Периодическая или бессрочная блокировка | То же, только для реальных активных дат | Исключение остаётся частью исходной структуры |
| Нерабочий праздник (`sunday = 0`) | Не проверяется | Игровой день исключается |
| Праздник как воскресенье (`sunday = 1`) | Не проверяется | Абонемент остаётся активным по фактическому дню недели |
